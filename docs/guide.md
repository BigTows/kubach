# Kubach — руководство

Подробности о сборке, хранилище kubeconfig и MCP. Обзор проекта — в [README](../README_RU.md).

Кроссплатформенная (macOS, Windows, Linux) Kubernetes IDE на Rust и
[GPUI](https://gpui.rs) ([GPUI Kit](https://gpui-kit.com)).

Kubach работает локально, с правами из вашего kubeconfig: в кластер ничего не
устанавливается ([ADR 0004](adr/0004-local-only.md)). Ещё он умеет быть MCP-сервером,
чтобы ИИ-агент (Claude Code, Claude Desktop) работал с кластером в заданных вами рамках.

## Сборка и запуск

Нужен Rust (edition 2024, свежий stable) и Git.

```sh
cargo run --release                        # приложение
cargo run -p kubach-ui --example gallery   # галерея дизайн-системы
```

Бинарь называется `kubach`. Для разработки хватает `cargo run`: dev-профиль уже
оптимизирует зависимости.

Иконка приложения лежит в [`crates/kubach-app/assets/icon`](../crates/kubach-app/assets/icon):
исходник `kubach.svg` и собранные из него (кубы на скруглённой тёмной подложке по сетке иконок Apple) `kubach.icns`, `kubach.ico` и `kubach-512.png` (она же — Dock при `cargo run`).
После правки SVG их пересобирает `cargo run -p kubach-app --example icons`.

- **macOS** — при `cargo run` иконку в Dock ставит само приложение. Подписанный
  `Kubach.app` собирает `scripts/bundle-macos.sh --profile <файл.provisionprofile>`
  (`--debug` — быстрая dev-сборка). Bundle ID и команда берутся из профиля, сертификат —
  из Keychain. Подпись с entitlement `keychain-access-groups` нужна для разблокировки
  хранилища по Touch ID ([ADR 0008](adr/0008-kubeconfig-vault.md)): при `cargo run`
  она недоступна. Нужен профиль macOS App Development (этот Mac в списке устройств) с
  сертификатом Apple Development или Developer ID с сертификатом Developer ID Application.
- **Windows** — иконка вшивается в `kubach.exe` при сборке.
- **Linux** — `dev.kubach.app.desktop` копируется в `~/.local/share/applications`,
  а `kubach-512.png` — в `~/.local/share/icons/hicolor/512x512/apps/dev.kubach.app.png`.

Системные зависимости определяет GPUI, в репозитории они не перечислены. Смотрите
требования GPUI для вашей ОС:

- **macOS** — Xcode (полный, не только Command Line Tools; нужен компилятор Metal).
- **Windows** — Visual Studio Build Tools с C++ и Windows SDK.
- **Linux** — компилятор C/C++, `pkg-config` и dev-пакеты для X11/Wayland, xkbcommon,
  Vulkan и fontconfig (см. ниже).

### Сборки и релизы

[`.github/workflows/build.yml`](../.github/workflows/build.yml) на каждый коммит в `main`
собирает пакеты для x64 и arm64 и кладёт их в артефакты run:

- **Linux** (Ubuntu 22.04, glibc 2.35) — `.deb`, `.rpm`, Arch `.pkg.tar.zst`, AppImage и
  `tar.gz` ([`scripts/package-linux.sh`](../scripts/package-linux.sh), nfpm и appimagetool).
- **macOS** — `Kubach.app` в `.dmg` (`scripts/bundle-macos.sh --dmg`).
- **Windows** — portable `zip` и MSI ([`scripts/package-windows.ps1`](../scripts/package-windows.ps1), WiX 5).

Релиз — это коммит в `main`, поднимающий версию в `Cargo.toml`: если тега с этой версией
(`2026.10.2`) ещё нет, run после сборки сам ставит тег и выкладывает те же файлы в
GitHub Release вместе с `SHA256SUMS` и PKGBUILD для AUR (`kubach-bin`). macOS-сборка подписывается и
нотаризуется, только если заданы секреты (список — в начале workflow). Без них у
приложения ad-hoc подпись: Touch ID недоступен, хранилище открывается паролем.

### Linux

Проверено на Debian 12 (bookworm) с актуальным stable Rust: `cargo build`,
`cargo clippy --workspace --all-targets -- -D warnings` и `cargo test --workspace`
проходят. Пакеты для Debian/Ubuntu (тот же список — в
[`.github/actions/linux-deps`](../.github/actions/linux-deps/action.yml)):

```sh
sudo apt-get install -y build-essential pkg-config \
  libxkbcommon-dev libxkbcommon-x11-dev libwayland-dev \
  libx11-dev libx11-xcb-dev libxcb1-dev \
  libfontconfig-dev libfreetype-dev libvulkan-dev \
  libssl-dev libzstd-dev
```

`libdbus` не нужен: D-Bus (logind, Secret Service) работает через чистый Rust `zbus`.
Для запуска нужен Vulkan-драйвер (на Debian/Ubuntu — `mesa-vulkan-drivers`).

Что зависит от окружения:

- **Настройки и хранилище** — в `$XDG_CONFIG_HOME/kubach` (по умолчанию `~/.config/kubach`)
  или в `KUBACH_CONFIG_DIR`.
- **Keychain** — Secret Service по D-Bus (GNOME Keyring, KWallet). Нужен только для режима
  «Keychain» у хранилища kubeconfig; если службы нет, режим недоступен с указанием
  причины, а пароль работает.
- **Блокировка по экрану** — свойство `LockedHint` сессии logind. Его выставляют
  GNOME, KDE и другие экраны блокировки, интегрированные с logind; без logind
  (контейнер, нет GUI-сессии) хранилище блокируется только вручную и по таймеру.
- **Окружение shell** — при запуске из `.desktop`-файла (без терминала) `PATH` и
  `KUBECONFIG` берутся из `$SHELL -l -i`, как на macOS.

## Подключение кластеров

Kubach читает `KUBECONFIG` (или `~/.kube/config`). Дополнительно кластеры добавляются
кнопкой «+» на панели кластеров («Add cluster») или в Settings → Clusters:

- **Link kubeconfig file** (по ссылке) — файл читается на месте и подмешивается после
  `KUBECONFIG`. Изменения от `aws`, `gcloud` и других утилит подхватываются, учётные
  данные остаются в вашем файле.
- **Import kubeconfig file** / **Paste kubeconfig from clipboard** — конфиг копируется в
  зашифрованное хранилище `vault.kubach` в папке настроек (`KUBACH_CONFIG_DIR` или
  папка ОС). Подходит для файлов, которые негде хранить: от коллеги или из облачной
  консоли. Шифрование — XChaCha20-Poly1305, ключ из пароля (Argon2id) и/или в системном
  хранилище ключей ([ADR 0008](adr/0008-kubeconfig-vault.md)). При импорте
  показывается предпросмотр контекстов; конфликтующие имена контекстов переименовываются.
- **Import from cloud…** — кластеры Google GKE, Yandex Cloud Managed Kubernetes и AWS EKS
  ([ADR 0019](adr/0019-cloud-import.md)). Kubach ищет CLI провайдера (`gcloud`, `yc`,
  `aws`) в `PATH`; если его нет, предлагает скачать официальный релиз в папку данных Kubach
  (прогресс и удаление — в Settings → Tools → Cloud CLIs; AWS CLI на Windows и CLI на
  Windows Arm — только подсказка установить самому). Если CLI не залогинен, показывается
  команда входа (`gcloud auth login`, `yc init`, `aws configure` / `aws sso login`).
  Дальше: выберите проекты / каталоги / регионы (и профиль для `yc` и `aws`), нажмите
  «Find clusters», отметьте кластеры и endpoint (внешний, внутренний или DNS для GKE) и
  «Next» — контексты строятся как у `get-credentials` / `update-kubeconfig` и сохраняются в
  хранилище. Для GKE нужен `gke-gcloud-auth-plugin` — окно предложит его поставить.
  Токены облака Kubach не хранит: при подключении контекст запускает CLI.
- **Блокировка хранилища** — расшифрованные конфиги живут только в памяти. Хранилище
  блокируется вручную («Lock imported clusters»), по таймеру бездействия (15 минут по
  умолчанию) и при блокировке экрана ОС; после этого сессии импортированных контекстов
  закрываются. Пароль спрашивается при первом подключении к такому контексту.
  Таймер и блокировка по экрану настраиваются в Settings → Clusters.

## MCP: ИИ-агенты

Агент не получает учётных данных: он видит только MCP-tools, а запросы к API делает Kubach
([ADR 0005](adr/0005-mcp-permissions.md)). Потолка нет (#15): у контекста есть **минимальный
доступ** — то, что агент получает без вопросов:

| Уровень | Что разрешено без вопроса |
|---------|---------------------------|
| Чтение (по умолчанию) | встроенные ресурсы (Pod, Deployment, Service, ConfigMap, Job, Ingress, events…) во всех namespace; Secrets недоступны совсем, даже метаданные |
| Отладка | чтение, плюс логи, exec и port-forward |
| Изменения | отладка, плюс apply, delete, scale, rollout restart, Helm |

Secrets (метаданные, проверки, раскрытие) и пользовательские ресурсы (CRD) — отдельные права.
Всё сверх минимума агент запрашивает, а Kubach спрашивает вас в своём окне: **Allow** — только
на эту сессию, с галочкой **«Разрешать по умолчанию»** — минимальный доступ контекста
поднимается в настройках (уровень целиком; Secret и CRD — отдельными отметками), и больше об
этом не спрашивают. Отказ действует до конца сессии. Ограничивает агента только ваш RBAC.

Подтверждение отдельных действий остаётся на любом уровне: diff перед apply, delete и Helm,
каждая команда exec, scale и rollout restart, запись Secrets. Для серии однотипных изменений в
окне есть галочка **«Не спрашивать до конца сессии: <действие> в <namespace>»**: такие же
действия в этом namespace дальше идут без окна, пока жива сессия (только в памяти, в настройки
не пишется). Delete, `helm_uninstall`, действия с нодами, Secrets, Helm от ваших учётных данных или
за пределами namespace и изменения с опасными полями спрашиваются всегда. Значения одного Secret агент
получает только с правом на Secrets, после отдельного вопроса на этот Secret с
предупреждением, что значение уйдёт провайдеру LLM, и только если значения Secrets не скрыты
от вас самих.

Много однотипных изменений агент делает одним вызовом: `scale_batch` и `rollout_restart_batch`
принимают список объектов или `labelSelector`, в одном namespace или в нескольких. Вы видите
**одно окно** со всеми объектами, которые изменятся, для scale — со старым и новым числом реплик,
и с тем, что в пакет не вошло и почему. Kubach находит объекты до вопроса и после него трогает
только их: объект, появившийся позже, агент увидит в ответе, но он не изменится. Если один объект
не удался, остальные продолжаются, а ответ называет каждый: что изменилось, что нет и почему.
Для scale ответ содержит исходные реплики и готовый вызов для отката. Галочки «Не спрашивать» в
этом окне нет. Окно пропускается только в одном случае: весь пакет лежит в одном namespace, и вы
уже выбрали «Не спрашивать» для этого действия там. В пакете не больше 200 объектов, лишнее не
отрезается: вызов просто откажет. `concurrency` у перезапуска — сколько запросов уходит
одновременно (1–16, по умолчанию 4). Это не число одновременных rollout: они идут уже после ответа.

На вопросы про весь кластер агент отвечает одним вызовом: `list_resources` и `list_events`
принимают `allNamespaces: true`, а `list_resources` — ещё `fieldSelector`, например
`spec.nodeName=<нода>`. Кластерных прав сессия при этом не получает: Kubach обходит namespace по
одному под идентичностью каждого, с теми же правилами, что и для одного namespace; Secrets
остаются недоступны, отозванные namespace не читаются. Сессия с `kubach mcp --namespace` читает
свои namespace без вопросов. В остальных сессиях namespace, с которыми агент ещё не работал,
Kubach открывает только после **одного** вопроса в окне со списком имён, потому что в каждом из
них появится временный ServiceAccount; ответ действует до конца сессии. Откажете — агент получит
то, что уже может прочитать. Ответ всегда начинается с покрытия: `Coverage: complete` или
`Coverage: PARTIAL` со списком непрочитанных namespace и причиной для каждого, поэтому
неполный результат нельзя принять за полный. `limit` у `list_resources` действует на namespace.

Helm-чарт с объектами уровня кластера (CRD, ClusterRole, webhooks, Namespace…) или с
Role/RoleBinding временный ServiceAccount поставить не может. Kubach находит их заранее через
`helm template`, без обращения к кластеру, и спрашивает: выполнить этот один вызов helm от
**ваших учётных данных из kubeconfig**? В окне — список таких объектов и галочка, по умолчанию
выключенная. Для install и upgrade после согласия Kubach делает пробный запуск от ваших
учётных данных и показывает diff во втором окне; меняется что-то только после него. Без
галочки ничего не выполняется, а агент получает перечень объектов. Для контекста из хранилища
всё так же: helm нужен файл, поэтому на время работы helm учётные данные этого контекста лежат
во временном файле, который можете прочитать только вы; после helm он удаляется, в том числе
при ошибке, а пока вы решаете в окне, файла нет.

Объекты чарта в другом namespace (например, Role для leader election, которую cert-manager
кладёт в `kube-system`) идут тем же путём. Сначала сессия получает права и на этот namespace,
как при любом обращении к нему; в сессии, закреплённой за своими namespace (`kubach mcp
--namespace`), это отказ. Затем в окне Helm такие объекты подписаны: «Role … (namespace
kube-system)», а в строке «Также меняет» перечислены эти namespace. Под временным
ServiceAccount это ещё одна причина спросить о ваших учётных данных. В остальных режимах
достаточно обычного окна с diff и галочки на эти объекты. `--create-namespace` по-прежнему
создаёт только namespace релиза.

Изменить в релизе одну-две настройки агент может, не видя values целиком: в `helm_upgrade`
он передаёт `valuesPatch` — только изменения, а Kubach сам сливает их с текущими values релиза
(mapping сливаются, списки и скаляры заменяются, `null` удаляет ключ). В окне Helm — diff
values «было/стало» с замаскированными секретами и обычный diff манифестов; агент получает
только этот замаскированный diff. Прочитать values релиза агент может через `helm_get_values`:
значения чувствительных ключей (`password`, `token`, `key`…) и строки, похожие на ключи и
токены (PEM, JWT, длинные base64 и hex), заменены на `*** (N bytes)`. Читает он их той же
идентичностью, что и историю релиза; временному ServiceAccount для этого нужен доступ к
Secrets — ваших учётных данных Kubach для этого не использует.

Namespace не спрашиваются, их число в сессии не ограничено; кластерные ресурсы и вызовы по
всем namespace недоступны. В каждом namespace Kubach сам создаёт временный ServiceAccount с
Role по правам сессии, если ваш RBAC это позволяет; иначе там действуют только ограничения
Kubach, и это помечено. Сессия живёт до выхода из Kubach (stdio — пока жив процесс), но не
дольше 8 ч. Выданное видно и отзывается в Settings → AI agent.

В Settings → Security для каждого контекста: «AI agent access» (включён по умолчанию, #9),
«Минимальный доступ» (уровень, отметки Secret и CRD, кнопка «Сбросить до чтения», история
поднятий) и «Скрывать значения Secret» — настройка для вас самих. Старые настройки потолка
(профиль, Protected cluster, TTL, число namespace и т. п.) игнорируются и в минимум не
переносятся.

### Обслуживание нод агентом

`cordon_node`, `uncordon_node` и `drain_node` меняют ноду, а это кластерный объект, поэтому вызов
идёт **от ваших учётных данных kubeconfig**, только этот один. Нужны доступ к нодам и уровень
«Изменения»: чего не хватает, Kubach спросит. Затем окно на каждый вызов с отдельной галочкой:
имя ноды и для drain все поды, в том числе из namespace, которых агент не видит. Галочки «не
спрашивать» здесь нет. Сессия `kubach mcp --namespace` ноды не меняет.

`drain_node` принимает `ignoreDaemonsets`, `deleteEmptyDirData`, `podSelector` (метки подов, нода
кордонится целиком) и `timeoutSeconds` (по умолчанию 300 с). С `preview: true` агент без вопроса
получает список: что будет выселено, что заблокировано PodDisruptionBudget, у каких подов нет
контроллера. Поды уходят только через Eviction API, бюджеты не обходятся. Параметра `force` нет:
поды без контроллера остаются на месте и попадают в отчёт. Выселяются только поды из окна; под,
пришедший на ноду после подтверждения, не трогается. После drain нода остаётся закордоненной, пока
не вызвать `uncordon_node`.

### Топология для агента

Два read-инструмента (#327, [ADR 0016](adr/0016-topology.md)) — права как у остальных
чтений: до 3 namespace за вызов, запись в аудит.

- `get_topology` — граф связей компактным JSON: узлы (id, kind, namespace, name, presence,
  поды, порты Service, хосты, изоляция NetworkPolicy), рёбра (маршруты, endpoints, ссылки на
  ConfigMap/Secret — только имена, вердикт политики) и диагностики с сообщениями. Параметры:
  `namespace` или `namespaces` (до 3), `resource` `{kind, name, namespace?}` с `depth` —
  окрестность ресурса, `detail` (`workloads`/`pods`), `networkPolicies` (по умолчанию `true`).
- `can_reach` — `from`, `to` (`{kind, name, namespace?}` workload/pod, `to` может быть
  Service, или `{address}` — IP вне кластера), `port` (номер или имя), `protocol` → разрешено
  ли соединение и почему: политики egress источника и ingress цели. Это анализ объектов
  NetworkPolicy; применяет ли их CNI — неизвестно.

Данные — одноразовый list нужных видов клиентом сессии; виды, которые политика или API не
дали, перечислены в `unavailable`, их узлы — `unknown`.

### Логи для агента

`get_logs` читает последние строки контейнеров, секреты в них маскируются до всех фильтров.
`filter` (подстрока или регулярное выражение с `regex`) ищет по тексту строки. `minLevel`
(`trace`, `debug`, `info`, `warn`, `error`, `fatal`) оставляет строки этого уровня и выше,
в каком бы формате они ни были (#117):

- logfmt и текст slog: `level=error`, `lvl=eror`, `level=ERROR+2`;
- JSON: поля `level`, `severity`, `lvl`, `loglevel`, `log_level`, `log.level`, числа pino и
  bunyan (10–60);
- klog: `E1103 12:34:56.789012 ...`.

Уровень не угадывается по словам в сообщении: `connection error` или `ERROR db failed` — это
строки без уровня, как и строки стектрейса. Такие строки в ответ не попадают, но считаются.
Заметка над строками говорит, сколько строк прочитано, у скольких распознан уровень и сколько
подошло:

```
(minLevel warn: 200 read, 150 with a recognized level, 3 matched; 50 without a recognized level were excluded)
```

Поэтому пустой результат понятен: при `150 with a recognized level` предупреждений в
прочитанных строках нет, а при `0 with a recognized level` заметка сообщает, что формат
незнаком и ответ об уровнях ничего не говорит. `minLevel` смотрит только на прочитанные строки
(`tailLines`, `sinceSeconds`); вместе с `filter` действуют оба условия.

### Port-forward для агента

Три инструмента (#17) — чтобы проверить сервис изнутри: health-эндпоинт, метрики, БД на время
отладки.

- `port_forward_start` — `target` (`pod/<имя>`, `service/<имя>` или `deployment/<имя>`; для
  Service и Deployment — готовый под по селектору, как в диалоге приложения), `port` (номер
  или имя порта; у Service — порт Service), необязательные `localPort` (1024–65535, по
  умолчанию свободный) и `namespace`. Возвращает `id` и `127.0.0.1:<порт>`.
- `port_forward_list` — forward-ы этой сессии: цель, порты, адрес, состояние, последняя ошибка.
  После работающих идут последние закрытые (до 16, новые первыми): `state: closed`, причина
  `reason` с пояснением `detail`, время `closedAt` и `lastError`.
- `port_forward_stop` — по `id`, только forward-ы этой сессии.

Нужен уровень «Отладка» (ниже — запрос доступа в окне Kubach) и чтение namespace; ваш RBAC
должен разрешать `pods/portforward`. Каждый forward подтверждается в окне Kubach (namespace,
цель, порты, сессия). Слушает только `127.0.0.1`, только TCP; в сессии не больше 8 forward-ов.
Forward-ы агента видны на экране **Port forwards** с пометкой «агент · <клиент>» — их можно
остановить, они не восстанавливаются при следующем запуске. У `kubach mcp` без приложения
forward живёт в процессе `kubach mcp`. Старт и стоп пишутся в аудит.

Forward закрывается только в этих случаях (значение `reason`):

| `reason` | Когда |
|----------|-------|
| `disconnected` | Агент отключился от Kubach по HTTP: закрыл свою последнюю сессию MCP или 2 минуты не было ни открытого потока (`GET` SSE), ни запросов. Сессия Kubach при этом продолжается |
| `session-ended` | Сессия закончилась: TTL, закрытие, выход из Kubach, конец stdin у `kubach mcp` |
| `revoked` | Вы отозвали чтение namespace |
| `user` | Вы остановили его на экране **Port forwards** |
| `agent` | Агент вызвал `port_forward_stop` |

Клиент без `GET`-потока, который молчит 2 минуты, например думает или ждёт долгую команду,
считается отключившимся. Если через forward в этот момент идёт соединение, forward дождётся его
конца и закроется в течение нескольких секунд после него; простаивающий закрывается сразу.
Закрытый forward не возобновляется: откройте новый через `port_forward_start`.

Перезапуск пода, обрыв или простой соединения forward не закрывают: локальный порт остаётся,
рвётся только это соединение. `port_forward_list` покажет `state: failing` и `lastError`,
следующее соединение пойдёт к поду заново, а у Service и Deployment — к другому готовому поду.

### Ожидание условия

Чтобы не опрашивать кластер, агент вызывает `wait_for_condition`: дождаться условия у объекта или
у всех объектов по `labelSelector`. Условие — статус (`Ready=True`, `Available=False`), `exists`
(объект появился) или `deleted` (объект исчез). Таймаут — `timeoutSeconds`: по умолчанию 120 с, не
больше 600 с, как у `wait_for_rollout`.

С `labelSelector` условие выполнено так: статус — у всех подходящих объектов, и хотя бы один
есть; `exists` — есть хотя бы один; `deleted` — не осталось ни одного. Условие статуса про старое
поколение объекта не считается, как в `kubectl wait`. `deleted` по имени следит за самим объектом:
новый объект с тем же именем не мешает.

Это чтение: те же права, вопросы и аудит, что у `get_resource` и `list_resources`. Первое обращение
к пользовательскому ресурсу спрашивает вас, а то, что читать нельзя, отказывает сразу, не дожидаясь
таймаута. Отозванное право, конец сессии и отмена вызова агентом прекращают ожидание. По таймауту
агент получает последнее состояние: что нашлось и какие объекты не подошли и почему.

### Два способа подключения

- **stdio** — `kubach mcp`, без окна; агент запускает его как дочерний процесс:

  ```text
  kubach mcp [--context NAME] [--namespace NS]... [--profile PROFILE] [--ttl DURATION] [--grant-read]
  ```

  `-c/--context` (по умолчанию стартовый контекст из настроек, иначе `current-context`),
  `-n/--namespace` (закрепляет сессию за namespace, можно повторять), `-p/--profile`
  (`read-only`, `debug`, `deploy`; ограничение этого процесса: больше этого уровня сессия не
  получит, запросы сверх него отклоняются без вопроса), `--ttl` (`30m`, `2h`, `1h30m` или
  минуты; по умолчанию и максимум 8 ч), `--grant-read` (оставлен для совместимости: чтение и
  так входит в минимальный доступ). Минимальный доступ берётся из настроек приложения.
  Подробнее — `kubach mcp --help`.
- **HTTP** — Settings → AI agent → «Serve MCP over HTTP». Сервер слушает
  `http://127.0.0.1:<порт>/mcp` (порт фиксированный), пока запущен Kubach, и требует
  bearer-токен. Токен хранится в папке настроек, читается только вами; его можно
  перевыпустить, старые конфиги агентов перестанут работать.

### Сниппеты

Готовые команды с подставленными путём, контекстом и токеном копируются из
Settings → AI agent → «Connect an agent». Вид такой:

```sh
# Claude Code, HTTP: работает в сессии, запущенной в приложении
claude mcp add --transport http kubach http://127.0.0.1:<порт>/mcp \
  --header "Authorization: Bearer <токен>"

# Claude Code, stdio
claude mcp add kubach -- /путь/к/kubach mcp \
  --context <context> --namespace <namespace>
```

Claude Desktop — в `claude_desktop_config.json` (Settings → Developer → Edit Config):

```json
{
  "mcpServers": {
    "kubach": {
      "command": "/путь/к/kubach",
      "args": ["mcp", "--context", "<context>", "--namespace", "<namespace>"]
    }
  }
}
```

### Подтверждения и аудит

Вопросы о правах и изменения (apply, delete, exec, scale, rollout restart, port-forward, Helm —
каждый вызов) подтверждаются в окне Kubach; для части из них можно отметить «Не спрашивать до
конца сессии» (см. выше), снять это можно кнопкой «Снова спрашивать» у сессии.
Для `kubach mcp` это значит, что приложение должно быть запущено с включённым HTTP-сервером,
иначе вызовы, которым нужен ответ пользователя, отклоняются. Активные сессии с их правами и
журнал аудита (без значений Secrets) видны в Settings → AI agent.

Вызов, который ждёт ответа, ждёт его до 5 минут. Агент узнаёт об этом сразу: клиенту с
`progressToken` приходит уведомление, остальные видят такие вызовы в `waitingForUser` у
`session_info`. Если окно Kubach скрыто или не в фокусе, приходит системное уведомление, клик по
нему открывает окно с вопросом; выключается в Settings → AI agent → «Notifications». На macOS
оно работает только из `Kubach.app`, на Linux нужен демон уведомлений.
