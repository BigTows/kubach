# 0008 — Зашифрованное хранилище импортированных kubeconfig

Статус: принято

## Контекст
Kubeconfig, которые негде хранить (прислал коллега, выгрузили из облачной консоли),
импортируются внутрь Kubach (#64). Режим «по ссылке» (#63) для них не подходит: файл
лежит где попало, обычно с правами `0644`, а копия в папке приложения — ещё одна
открытая копия секретов. Импортированные конфиги нужно хранить зашифрованными,
одинаково на macOS, Windows и Linux, а ключ — паролем и/или в системном хранилище
ключей.

Рассмотренные варианты формата:
- **`age` с passphrase.** Готовый проверенный формат, но passphrase-получатель в `age`
  обязан быть единственным (scrypt-стенза не сочетается с другими), так что режим
  «пароль + Keychain» потребовал бы двух копий данных или своей обёртки над ключом.
  KDF — scrypt без выбора параметров со стороны приложения.
- **Свой контейнер: AEAD XChaCha20-Poly1305 + Argon2id.** Примитивы из RustCrypto
  (`chacha20poly1305`, `argon2`) — чистый Rust, аудированные, одна и та же реализация на
  всех ОС. Позволяет несколько «слотов» ключа над одним ключом данных (как LUKS).

## Решение
**Формат `vault.kubach`** — JSON-конверт в папке настроек (`KUBACH_CONFIG_DIR` или
папка ОС), права `0600` на Unix, на Windows — DACL только с текущим пользователем
(наследование от папки отключено, `windows-sys`), запись атомарная (временный файл +
rename):

```json
{
  "format": "kubach-vault", "version": 1,
  "entries": [{ "id": "…", "name": "eks-prod", "contexts": ["prod"] }],
  "slots": [
    { "kind": "password", "kdf": { "alg": "argon2id", "m_cost": 65536, "t_cost": 3,
      "p_cost": 1, "salt": "<16 байт>" }, "nonce": "<24 байта>", "wrapped_key": "…" },
    { "kind": "keychain", "account": "<uuid хранилища>" },
    { "kind": "biometric", "account": "<uuid>", "nonce": "<24 байта>", "wrapped_key": "…" }
  ],
  "nonce": "<24 байта>", "ciphertext": "…"
}
```

- Данные (все импортированные kubeconfig) шифруются случайным 256-битным **ключом
  данных** (DEK) алгоритмом XChaCha20-Poly1305 со случайным 192-битным nonce на каждую
  запись файла. Открытая часть заголовка (`format`, `version`, `entries`) входит в AAD:
  подмена списка контекстов обнаруживается при расшифровке.
- **Слот «пароль»:** KEK = Argon2id(пароль, соль) с параметрами из заголовка; DEK лежит
  зашифрованным KEK (тот же AEAD, свой nonce, AAD `kubach-vault/1/password`).
  Параметры по умолчанию: 64 МиБ, 3 прохода, 1 поток (RFC 9106, второй рекомендуемый
  набор по памяти; ≈0,3–0,5 с на современном ноутбуке). Параметры хранятся в файле, их
  можно поднять в следующих версиях без миграции. При чтении заголовка они проверяются
  до любой деривации: `m_cost` ≤ 1 ГиБ, `t_cost` ≤ 16, `p_cost` ≤ 16 (и минимумы
  Argon2). Значения вне пределов — ошибка «повреждённый файл» без аллокации: испорченный
  или подложенный файл не заставит Kubach выделить гигабайты памяти или считать минутами.
- **Слот «Keychain»:** DEK лежит в системном хранилище ключей (крейт `keyring`: Keychain
  на macOS, Credential Manager на Windows, Secret Service на Linux) под сервисом
  `kubach-vault` и случайным `account` из заголовка.
- **Слот «биометрия»** (#80): DEK зашифрован ключом KEK (тот же AEAD, AAD
  `kubach-vault/1/biometric`), который ОС отдаёт только после Touch ID / Windows Hello
  (`kubach_core::vault::biometric`, трейт `BiometricStore`):
  - **macOS** — случайный 256-битный KEK в Keychain (data protection keychain,
    `kSecUseDataProtectionKeychain`) с access control `biometryCurrentSet` и
    `WhenPasscodeSetThisDeviceOnly` (`security-framework`). Touch ID запрашивает сама ОС
    при чтении элемента; при добавлении или удалении отпечатка элемент становится
    недоступен (`errSecItemNotFound`) — понятное сообщение и пароль, включить заново в
    настройках. Слабый вариант «проверить LAContext и прочитать обычный Keychain» не
    используется: без биометрии ОС ключ не отдаёт. Data protection keychain требует
    подписанной сборки с entitlement; неподписанная (dev) получает
    `errSecMissingEntitlement` (`-34018`) — режим помечается недоступным, работает пароль.
    Доступность проверяется добавлением и удалением пробного элемента (без запроса).
  - **Windows** — Windows Hello (`KeyCredentialManager`, закрытый ключ в TPM), имя
    `kubach-vault-biometric-<account>`. KEK = SHA-256 от RSA-подписи фиксированного
    challenge: подпись PKCS#1 v1.5 детерминирована, а получить её можно только через
    Hello. Доступность — `KeyCredentialManager::IsSupportedAsync`.
  - **Linux** — режим недоступен, пароль.

  Биометрия — дополнительный способ, а не замена: включается только при наличии слота
  «пароль». При разблокировке сначала биометрия (диалог «Confirm with Touch ID…» с
  кнопкой «Use password»), затем Keychain; отмена, ошибка или смена отпечатков —
  поле пароля с причиной. Порядок и fallback — в `kubach-core`
  (`KeyMode::automatic`, `LockedVault::unlock_without_password`,
  `VaultError::falls_back_to_password`) с тестами на фейковом хранилище. Смена пароля
  создаёт новый биометрический ключ; если ОС его не выдала — биометрия выключается, а
  пароль всё равно меняется. Сброс удаляет и биометрический ключ.
- Режимы ключа на выбор пользователя: только пароль (основной, работает везде), только
  Keychain, пароль + «запомнить в Keychain» (оба слота). Если Secret Service на Linux
  недоступен, Keychain-режим неактивен с объяснением — пароль остаётся.
- **Смена пароля** — новый DEK, полная перешифровка данных и всех слотов (обновляется и
  запись в Keychain). Старый файл заменяется атомарно.
- **Блокировка:** DEK и расшифрованные конфиги живут только в памяти процесса
  (`zeroize` при блокировке и выходе). Блокировка вручную и по таймеру бездействия
  (настройка, по умолчанию 15 минут), а также при блокировке экрана ОС (настройка
  «Lock when the screen locks», по умолчанию включена); после блокировки сессии импортированных
  контекстов закрываются — и подключения кластеров, и сессии MCP-агента (#121): HTTP-сессия
  приложения на импортированном контексте и сессии, которые приложение ведёт для `kubach mcp`. Пароль спрашивается при первом подключении к импортированному
  контексту — диалогом внутри главного окна.
- **Ошибки:** неверный пароль — понятная ошибка и растущая задержка после трёх неудачных
  попыток. Файл, который не разбирается или не расшифровывается при верном ключе,
  считается повреждённым: он не перезаписывается, рядом сохраняется копия
  `vault.kubach.corrupt-<время>`, хранилище можно только сбросить. Сброс после явного
  предупреждения удаляет файл, эти копии и недописанный `vault.kubach.tmp` (только по
  точному шаблону имени), запись в Keychain и биометрический ключ. Если заголовок файла не
  читается, учётные записи Keychain берутся из резервных копий; если не нашлись и там
  (или Keychain отказал в удалении), пользователь получает предупреждение, что искать
  записи `kubach-vault` в Keychain нужно вручную.
- **Слияние с остальными kubeconfig:** импортированные конфиги подмешиваются после
  `KUBECONFIG`/`~/.kube/config` и связанных файлов. Конфликты имён контекстов
  разрешаются переименованием при импорте: сначала автоматически (`-imported`), затем
  пользователь может переименовать каждый контекст в предпросмотре; пустые, повторяющиеся
  и занятые имена подсвечиваются на лету и блокируют импорт (`ImportPlan::problem`); имена кластеров и пользователей, уже занятые
  предыдущими файлами, переименовываются при загрузке, чтобы импортированный контекст
  никогда не взял чужие учётные данные.
- **Изоляция имён связанных файлов** (#188): то же переименование (`isolate_names`)
  применяется и к файлам «по ссылке» (суффикс — имя файла без расширения), иначе при
  слиянии kube-rs «первое имя выигрывает», и перетащенный файл с `user: kubernetes-admin`
  и своим сервером отправил бы туда учётные данные из `~/.kube/config`, а второй
  kubeadm-конфиг с `cluster: kubernetes` молча ходил бы в первый кластер. Контекст,
  ссылающийся на кластер или пользователя, которых его файл не определяет, но определяет
  более ранний, получает несуществующее имя: kube-rs сообщает об отсутствующем кластере
  или подключается без учётных данных, но не берёт чужие. Ссылки между файлами связанных
  kubeconfig поэтому не работают; файлы из `KUBECONFIG` сливаются по правилам kubectl.
- **Ручное добавление** (#97, «+» → Add cluster → Add manually…): форма (URL API-сервера,
  CA или `insecure-skip-tls-verify`, token / client cert+key / exec-плагин) собирается в
  kubeconfig с одним контекстом (`vault::manual`), вкладка YAML принимает kubeconfig
  целиком. Дальше — тот же `ImportPlan`, предпросмотр и переименование конфликтов, что
  у импорта. «Test connection» до сохранения запрашивает `/version` и переводит ошибку в
  понятный текст (`kubach_core::probe`: 401/403, TLS, DNS, отказ, таймаут, exec-плагин);
  на диск при этом ничего не пишется.
- **Способы входа ручного добавления** (#120), все собираются в обычный kubeconfig и
  разбираются из YAML обратно в форму:
  - **Логин + пароль** — `username`/`password` (basic auth, kube-rs поддерживает); пароль
    в форме маскируется и живёт в `Zeroizing`. С Kubernetes 1.19 API-сервер basic auth
    не отвергает (401), а молча игнорирует и считает запрос анонимным, а `/version`
    анонимам открыт. Поэтому «Test connection» после `/version` спрашивает
    `SelfSubjectReview` (1.28+): `system:anonymous` в ответе или в отказе 403 —
    отдельная ошибка «сервер проигнорировал учётные данные»; если сервер ответить не
    может, проверка считается пройденной, как раньше.
  - **OIDC — только через exec-плагин kubelogin**: `kubectl oidc-login get-token
    --oidc-issuer-url=… --oidc-client-id=… [--oidc-client-secret=…]
    [--oidc-extra-scope=…]`, `apiVersion: client.authentication.k8s.io/v1beta1`.
    `auth-provider: oidc` не используется: встроенные auth-provider в client-go
    устарели в пользу exec-плагинов (gcp и azure удалены в 1.26), в kube-rs oidc — за
    отдельной фичей `oidc`, и он не умеет первичный вход — только
    обновление уже полученного refresh token, который пришлось бы вставлять руками.
    kubelogin сам открывает браузер, кэширует и обновляет токены (`~/.kube/cache/oidc-login`),
    поэтому поля refresh token в форме нет. Exec-плагин ровно такой формы разбирается
    обратно в OIDC-поля; с другими флагами kubelogin — остаётся «Exec plugin».
    Client secret лежит в аргументах (в хранилище — зашифрованным), в предпросмотре
    импорта маскируется.
  - **Шаблоны exec** (`ExecTemplate`): EKS — `aws [--region R] eks get-token
    --cluster-name C --output json`, профиль через `env AWS_PROFILE` (как пишет
    `aws eks update-kubeconfig`); GKE — `gke-gcloud-auth-plugin`; AKS — `kubelogin
    get-token --login azurecli --server-id <id>` (по умолчанию id AKS-managed Entra ID).
    Выбор шаблона показывает его поля и итоговую команду; «Custom» переносит её в
    обычные поля exec. Exec-плагин, совпадающий с шаблоном, при разборе YAML открывается
    в шаблоне.
  - Если программа плагина не найдена в `PATH` (уже взятом из login shell при старте;
    `PATH` из env плагина имеет приоритет) — предупреждение с подсказкой установки.
    «Test connection» отличает `kubectl` без плагина `oidc-login` (`unknown command`) от
    прочих сбоев exec как «команда не найдена».

- **Блокировка экрана ОС** (`kubach_core::vault::screen_lock`): пока хранилище
  разблокировано, приложение раз в 2 с спрашивает ОС в фоне: macOS —
  `CGSSessionScreenIsLocked` из `CGSessionCopyCurrentDictionary`; Windows —
  `WTSQuerySessionInformationW(WTSSessionInfoEx)`, флаг `WTS_SESSIONSTATE_LOCK`;
  Linux — свойство `LockedHint` сессии logind (`org.freedesktop.login1`, сессия `auto`)
  через `zbus`, который уже есть в дереве. Опрос вместо подписки на уведомления не
  требует оконной процедуры, наблюдателя run loop или D-Bus-сигналов. Если ОС ответить
  не может (нет GUI-сессии или logind), хранилище просто не блокируется по экрану.
- **Системный keychain, биометрия и Argon2id — только в фоне.** Разблокировка, создание,
  смена пароля, включение/выключение Keychain и биометрии, проверка доступности и сброс
  выполняются вне UI-потока: keychain может показать системный запрос или ждать D-Bus,
  Touch ID / Windows Hello ждут пользователя. Изменения идут над копией
  разблокированного хранилища, которая затем подменяет текущую; пока операция идёт,
  хранилище «занято», другие изменения отклоняются, кнопки показывают «…».

## Модель угроз
- **Кража файла / бэкапы / синхронизация папки настроек.** Без пароля (или доступа к
  Keychain пользователя) из файла не извлечь ни серверы, ни сертификаты, ни токены.
  Перебор паролей замедляет Argon2id. В открытом виде остаются только имена
  импортированных записей и их контекстов — чтобы показывать плитки до разблокировки.
- **Другой пользователь на машине.** Файл `0600` (Windows — DACL только для владельца в per-user `%APPDATA%`); даже
  при чтении файла нужен пароль. Keychain-режим защищён учётной записью ОС;
  биометрический — ещё и присутствием пользователя (Touch ID / Windows Hello), ключ не
  покидает устройство (`ThisDeviceOnly`, TPM).
- **Вредоносный процесс того же пользователя** при разблокированном хранилище читает
  память процесса — вне модели угроз (как у любого менеджера паролей).
- **Программы и локальные файлы чужого kubeconfig** (#185, #187, #188). Предпросмотры
  импорта и привязки (в том числе drag&drop на окно) показывают один и тот же блок
  (`kubeconfig::review::ConfigReview` в `kubach-core`, `review_section` в приложении):
  - программы, которые запускаются при подключении: `exec` (команда, аргументы и `env`)
    и `auth-provider` с `cmd-path`/`cmd-args` (kube-rs запускает его для `gcp`;
    показывается при любом имени провайдера). Переменные окружения, которые заставляют
    безобидную программу выполнить чужой код (`PATH`, `BROWSER`, `EDITOR`, `PYTHON*`,
    `NODE_*`, `LD_*`, `DYLD_*`, `PERL5OPT`, `RUBYOPT`, `JAVA_TOOL_OPTIONS`,
    `AWS_CONFIG_FILE` и подобные, `is_dangerous_env`), выделяются красным. Импорт они не
    блокируют: у легитимных плагинов бывает свой `PATH`;
  - локальные файлы, которые встраиваются (импорт) или читаются при подключении
    (привязка): `certificate-authority`, `client-certificate`, `client-key`, `tokenFile` —
    поле, владелец и путь. Пути вне папки исходного kubeconfig (с разрешением symlink и
    `..`) выделяются красным: так `tokenFile: ~/.npmrc` не уйдёт молча на чужой сервер
    в `Authorization: Bearer`.
  - **Вставленный YAML** (буфер обмена, вкладка YAML ручного добавления) не имеет папки и
    приходит неизвестно откуда, поэтому его файлы не читаются, пока пользователь не
    отметит «Read these files into the vault» (`ImportPlan::read_files`). До этого план
    нельзя сохранить (`VaultError::UnreadFiles` в `Vault::add`/`replace`), а «Test
    connection» подключается без этих файлов (`ImportPlan::to_contexts` их убирает).
    Хранить ссылки без чтения нельзя: kube-rs всё равно прочитал бы их при подключении.
- Расшифрованный конфиг никогда не пишется на диск, в логи, в журнал аудита MCP и в
  тексты ошибок. Экспорт в открытый kubeconfig — только явным действием с
  предупреждением.
- **AI-агент.** Расшифрованный конфиг не покидает процесс приложения и для MCP: процесс
  `kubach mcp` читает только открытый заголовок (имена контекстов), а сессию на
  импортированном контексте ведёт приложение, пока хранилище разблокировано
  ([ADR 0005](0005-mcp-permissions.md), «Контексты из хранилища»). Агент, получивший prompt
  injection, не может «попросить» процесс расшифровать хранилище: у процесса нет ни ключа,
  ни способа его получить.

## Отличие от режима «по ссылке» (#63)
| | По ссылке | Импорт |
|---|---|---|
| Где лежит | Файл пользователя, читается на месте | Копия внутри `vault.kubach` |
| Обновления от `aws`/`gcloud` | Подхватываются автоматически | Только «Обновить из файла» |
| Секреты на диске | Как у исходного файла | Только зашифрованными |
| Доступ | Всегда | После разблокировки |

## Последствия
- Новые зависимости: `chacha20poly1305`, `argon2`, `zeroize`, `keyring` (через
  `[workspace.dependencies]`); на Linux — `zbus` для logind (#87); на macOS —
  `security-framework` и `core-foundation`, на Windows — `windows` (#80; все уже были в
  дереве через `keyring` и gpui).
- `Source::Imported` — новый источник контекстов; заблокированное хранилище даёт
  контексты без конфигурации, они показываются со значком замка.
- MCP (#12) видит импортированные контексты только при разблокированном хранилище и по
  правилам ADR 0005; `kubach mcp` получает их только через мост к запущенному приложению
  (сессию ведёт приложение), standalone без приложения — понятная подсказка вместо
  инструментов (#121).
- Формат версионирован (`version`); изменение примитивов или структуры — новый ADR и
  миграция при разблокировке.
- Блокировка может сама сменить активный контекст (перезагрузка kubeconfig → подключение
  к current-context), поэтому изменяющие действия захватывают `Connection` в момент
  запроса и выполняются, только пока она остаётся активной (`Connection::same_as`,
  `kubach-app/src/action_context.rs`, #344): confirm-диалоги показывают контекст и
  закрываются при его смене, вкладки терминала и логов остаются в своём контексте.
