# 0014 — Разрывы watch и соединения с API

Статус: принято

## Контекст
На удалённых кластерах (за балансировщиком, например LKE) соединения watch рвутся
регулярно: idle-таймаут балансировщика, перезапуск API-сервера, истёкший resource version
(#316). Раньше:
- любая ошибка `kube::runtime::watcher` сразу становилась `WatchStatus::Error` — красный
  баннер с сырой цепочкой ошибок;
- watcher после ошибки сам переподключается с того же resource version, но **молча**: ни
  одного события, пока не изменится какой-нибудь объект. В тихом кластере статус оставался
  `Error` бесконечно, а `sync_summary` считал такой watch «reconnecting» — индикатор
  синхронизации и `LoadingBar` в статус-баре не гасли;
- мёртвое соединение из пула валило следующий запрос (bulk delete падал с `ServiceError`).

## Решение
- **Повтор на свежем watcher.** `cache::run` при ошибке потока бросает его и через backoff
  (1 с, удваивается до 30 с, сброс при восстановлении) открывает новый — тот делает
  relist, и `InitDone` явно сообщает о восстановлении. Цена — полный list (из watch-cache
  API-сервера, `any_semantic`) после каждого разрыва вместо возобновления с resource
  version.
- **Relist не копирует неизменённое** (#168). Пока идёт relist, старый список остаётся
  видимым, а новый копится рядом и подменяет его на `InitDone`. Объект, который сервер
  вернул с теми же `uid` и `resourceVersion`, в новый список попадает прежним `Arc`, а
  не новой копией: второй копии кэша на время relist нет, и по `Arc::ptr_eq` читатель
  видит, что объект не менялся (на это опирается кэш строк таблицы). Сравнение идёт по
  метаданным от сервера, до маскирования, поэтому работает и для Secrets. Объект без
  `uid` или `resourceVersion` всегда заменяется.
- **Что кэш не хранит** (#168). На входе в кэш (`ObjectStore::prepare`) у объекта
  удаляются `metadata.managedFields` и аннотация
  `kubectl.kubernetes.io/last-applied-configuration` (полная копия манифеста) — у всех
  видов, и из list, и из watch. Из кэша их никто не читает: редактор и ревью правок берут
  объект свежим GET, apply — тоже, дисковый кэш списков ([ADR 0012](0012-list-cache.md))
  и MCP вырезают эти поля сами. На объектах minikube это 36 % JSON у Pod, 54 % у
  Deployment, 47 % у ReplicaSet, 46 % у Service, 5 % у ConfigMap (размер сериализованных
  объектов, не память приложения). У Secrets, как и раньше, дополнительно убираются
  значения.
- **Порог ошибки** (`cache::outage`). Кратковременный разрыв не ошибка: статус остаётся
  прежним (`Ready` или `Loading`), watch лишь помечен «reconnecting». Ошибка показывается,
  если watch не восстановился за `ERROR_AFTER` (12 с), после `ERROR_AFTER_FAILURES` (5)
  неудач подряд или сразу при 403.
- **Watch CRD** (`discovery::crd_changes`, по нему перезапускается discovery) — один
  watcher на подключение, без статуса в UI. После ошибки следующий опрос watcher
  откладывается на тот же backoff (`Outage::retry_delay`: 1 с, удваивается до 30 с, сброс
  при восстановлении) — сам watcher повторяет запрос сразу, как только его опросят. При
  403 (нет права `list customresourcedefinitions`, обычное дело при RBAC на namespace) и
  404 (API CRD нет) поток завершается: повтор даст тот же ответ. Приложение работает без
  уведомлений об изменении CRD, каталог обновляется при следующем подключении; новая
  попытка watch — тоже при следующем подключении. 401 и прочие ошибки повторяются с
  backoff (учётные данные могут обновиться). Повторный list после потери позиции watch
  (410) считается изменением: события за время разрыва пропущены (#167).
- **Статус-бар.** `LoadingBar` и «Syncing…» — только пока грузится список
  (`SyncSummary::is_loading`); переподключение — «Reconnecting…» с неподвижной иконкой и
  без прогресс-бара. Watch, потерявший соединение до первого list, считается
  переподключающимся, а не загружающимся.
- **Баннер** говорит по-человечески («Lost connection to the cluster, showing cached
  data. Retrying…»; `WatchError::connection` отличает обрыв соединения от ответа API),
  сырая ошибка — в tooltip.
- **Транспорт** (`kubach-core::transport`, используется `redact::client`): тот же стек, что
  у `ClientBuilder::try_from`, плюс TCP keepalive (30 с, пробы каждые 10 с), pool idle
  timeout 50 с (ниже типичного idle-таймаута балансировщиков) и один повтор идемпотентного
  запроса (GET, HEAD, OPTIONS, DELETE) при ошибке соединения — но не при HTTP-ответе
  API и не при таймауте. Серверный retry kube-rs (429/503/504, backoff и `Retry-After`)
  включён только для безопасных запросов (GET, HEAD, OPTIONS): POST/PUT/PATCH/DELETE
  с таким ответом сразу возвращают ошибку, чтобы отказ PDB при выселении не крутился
  минутами, а POST с прошедшей записью не создал второй объект (#345). WebSocket-upgrade
  (exec, attach, port-forward) не повторяется ни одним из механизмов. DELETE известного
  объекта несёт `preconditions.uid`: пересозданный объект с тем же именем не удаляется
  (409 → «объект был пересоздан»), а 404 считается успехом — в т. ч. когда первый DELETE
  прошёл, а ответ потерялся при обрыве. kube-rs договаривается только о HTTP/1.1, поэтому HTTP/2 ping
  неприменим. Для кластеров за прокси (`proxy-url`) остаётся стек kube-rs без этих
  добавок.

## Последствия
- Мигание сети не видно пользователю; устойчивая ошибка видна через ~12 с.
- После каждого разрыва — relist; для очень больших видов это заметный трафик (но не
  вторая копия в памяти: неизменённые объекты переиспользуются).
- В деталях ресурса аннотация `last-applied-configuration` больше не показывается (у
  ConfigMap она и раньше была скрыта плейсхолдером); `managedFields` виден только в
  YAML свежего GET. Тому, кому эти поля понадобятся из кэша, нужен отдельный GET.
- Свой стек клиента нужно сверять с `kube-client` при обновлении kube-rs (слои
  `base_uri`, retry, auth, extra headers).
