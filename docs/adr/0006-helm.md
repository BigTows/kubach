# 0006 — Helm: чтение нативно, изменения через `helm` CLI

Статус: принято

## Контекст
Kubach показывает Helm-релизы (#15). Helm 3 хранит каждую ревизию в Secret
(`helm.sh/release.v1`) или ConfigMap: `base64(gzip(JSON))` релиза с чартом, values,
манифестом и хуками. Нужны также rollback, uninstall и upgrade. Upgrade требует рендера
чарта (Go templates + Sprig, `lookup`, сабчарты, репозитории, OCI) — на Rust его не
повторить. Rollback и uninstall формально проще, но включают хуки (с весами и delete
policies), 3-way merge, `helm.sh/resource-policy: keep`, ожидание готовности и
запись ревизий в хранилище, которое потом читает `helm` пользователя.

## Решение
- Чтение (список, история, values, манифест, хуки, diff) — нативно в `kubach-core::helm`,
  без бинаря `helm`, по правам из kubeconfig.
- Изменения (rollback, uninstall, upgrade, install, операции с репозиториями) — вызовом установленного у пользователя `helm`
  (поиск в `PATH`, путь настраивается). Kubach не бандлит бинарь и не пишет в хранилище
  релизов сам. Вызов всегда с явными `--kube-context`, `--kubeconfig`, `--namespace` и
  `HELM_DRIVER`, совпадающими с открытым подключением.
- Нет `helm` — действия недоступны с подсказкой и предложением скачать его (ниже);
  просмотр работает.

### Uninstall и upgrade (#99)
- Uninstall: `helm uninstall <release> [--keep-history]`. Перед подтверждением
  перечень ресурсов строится нативно из манифеста последней ревизии (с пометкой
  `helm.sh/resource-policy: keep`) и число delete-хуков; имя релиза нужно ввести.
- Upgrade: `helm upgrade <release> <chart> --reset-values --values -`. Values
  передаются через stdin, не через файл и не через `--set`: в командной строке и на
  диске их нет. `--reset-values` делает текст из редактора полным набором
  пользовательских values поверх дефолтов чарта — ровно то, что видно в редакторе.
- Чарт по умолчанию — тот, что хранится в релизе: Kubach записывает его во временную
  папку (права 0700, удаляется после вызова), имена файлов вне папки чарта
  отклоняются. Helm не сохраняет в релизе сабчарты, поэтому чарт с `dependencies`
  так не обновить — тогда пользователь указывает `repo/chart`, `oci://…`, путь или
  URL (и `--version`); их разрешает `helm` пользователя (его репозитории и логины).
- Предпросмотр: тот же вызов с `--dry-run=server --output json` (нужен Helm ≥ 3.13):
  рендер с `lookup` и проверкой на API-сервере, без записи. Из JSON берётся манифест;
  diff с текущим манифестом и список добавленных/изменённых/удалённых объектов
  строятся нативно. Применить можно только предпросмотренный ввод: правка values или
  чарта после предпросмотра требует нового.

### Новая версия чарта, версия селектом, PVC при uninstall (#273)
- Новая версия ищется нативно, без сети и без `helm`, в закэшированных `index.yaml`
  репозиториев пользователя (`kubach-core::helm::updates`). В релизе нет репозитория,
  из которого ставился чарт, поэтому он ищется по имени чарта; если чарт есть в
  нескольких репозиториях, выбирается тот, чьи `home`/`sources` в индексе совпадают с
  `home`/`sources` из `Chart.yaml` релиза (или ссылка из них лежит под URL репозитория).
  Неоднозначно (зеркала с теми же метаданными) или не найдено — новая версия не
  показывается. Сравнение — SemVer; pre-release предлагается, только если установлен
  pre-release. В списке — значок `↑ x.y.z` у чарта с тултипом, в карточке —
  плашка «New version … available in repo …» с Upgrade, открывающим панель на этой версии.
  Индексы перечитываются при показе Releases и после команд с репозиториями
  (неизменённые не разбираются повторно).
- Upgrade: если чарт найден в репозиториях, по умолчанию — `repo/chart` и версия
  из списка версий индекса (с пометками current, app version, pre-release), при
  нескольких кандидатах — выбор репозитория. Чарт из релиза остаётся вариантом.
  Ручной ввод ссылки (`oci://…`, путь, URL) — только если ни в одном репозитории
  чарта нет.
- Uninstall: перед подтверждением нативно ищутся PVC, которые `helm uninstall`
  оставит (`kubach-core::helm::claims`): в namespace релиза с меткой
  `app.kubernetes.io/instance=<release>` или `release=<release>`, либо созданные
  StatefulSet'ами манифеста из `volumeClaimTemplates` (`<template>-<sts>-<n>`); PVC из
  самого манифеста не показываются (helm их удаляет), кроме помеченных
  `helm.sh/resource-policy: keep`. Они перечисляются в подтверждении с галочкой
  «Also delete these PVCs» (по умолчанию выключена). Удаление — только после успешного
  uninstall, по одной PVC через Delete плагина PVC (#274), не через `helm`; итог —
  в отдельном уведомлении. Kubach в хранилище релизов при этом не пишет.

### Драйвер хранения и живой список (#102)
- Список релизов следит за кластером через общий кэш (`ResourceCache`): watch на
  Secret (`type=helm.sh/release.v1`) и ConfigMap с меткой `owner=helm`, **только
  метаданные** (`PartialObjectMeta`) — метки дают релиз, ревизию и статус, тела с
  values по сети не гоняются и в кэше не лежат. Всплеск событий схлопывается
  дебаунсом кэша. По снимку вычисляется последняя ревизия каждого релиза; заново
  читается и декодируется только тот релиз, у последнего объекта которого сменились
  имя или `resourceVersion` (`helm::live::ReleaseFeed`). Открытый релиз
  перечитывается так же; исчезнувший (uninstall без истории) закрывается. Кнопка
  Refresh остаётся как принудительное перечитывание, для свежести она не нужна.
- Драйвер (`secret` / `configmap`) задаётся в настройках контекста
  (`clusters.helm_drivers`, Settings → Clusters). Не задан — определяется по тем же
  watch: где больше релизов в выбранных namespace, при равенстве и без релизов —
  Secret (умолчание Helm). Выбранный драйвер используется и для чтения, и как
  `HELM_DRIVER` во всех вызовах `helm`. `sql` и `memory` не поддерживаются.

### Загрузка `helm` по запросу (#131)
- Порядок поиска: `tools.helm_path` из настроек → `helm` в `PATH` → копия, скачанная
  Kubach (`kubach_core::settings::Tools::locate_helm`).
- Kubach не бандлит `helm`, но может скачать официальный релиз с `get.helm.sh` —
  **только по явному действию** («Download Helm» в подсказке на экране Helm, Download /
  Update в Settings → Tools), без фоновых и автоматических загрузок. Проверка новой
  версии — ниже (#403).
- Архив скачивается во временный каталог рядом с местом установки; его SHA-256
  сверяется с `.sha256sum` с `get.helm.sh` и дальше — с зашитым хэшем или с подписью
  (ниже). Не совпал — файл удаляется, показывается ошибка. Из архива берётся только
  файл `helm[.exe]`
  (пути других записей не используются), на Unix ставится `0755`, на macOS снимается
  `com.apple.quarantine`, затем каталог версии атомарно переименовывается в
  `<data_dir>/kubach/tools/helm/<ver>/` (`KUBACH_DATA_DIR`, иначе `KUBACH_CONFIG_DIR`
  переопределяют папку). Отмена или ошибка удаляют временный каталог. После успешного
  обновления старые версии удаляются; в Settings → Tools видно, какой `helm` используется
  (путь, источник, `helm version`, чем проверен), и скачанный можно удалить.
- В систему ничего не ставится: ни `PATH`, ни `/usr/local/bin`, ни реестр Windows,
  прав администратора не нужно. Скачанный `helm` запускается так же, как системный
  (те же `--kube-context`, `--kubeconfig`, `HELM_DRIVER`) и с обычными путями
  конфигурации Helm пользователя: репозитории и логины общие с системным `helm`.
- HTTP-клиент — уже имеющийся в дереве (`kube::Client`: hyper + rustls, системные
  корневые сертификаты); прокси берётся из `HTTPS_PROXY` / `ALL_PROXY` с учётом
  `NO_PROXY` (http CONNECT и SOCKS5). Механизм общий (`kubach_core::tools::ToolSpec`):
  следующий инструмент (например, kustomize) добавляется описанием артефактов.
- Это исключение из ADR 0004 (только локальная работа): сетевой запрос не к кластеру,
  выполняется с явного согласия пользователя, в кластер ничего не ставится. Второе
  исключение — иконки чартов и картинки README (ниже).

### Актуальная версия и подпись релиза (#403)
- Линия: Helm 4 (по умолчанию) или Helm 3 — `tools.helm_line` (`"4"` / `"3"`),
  Settings → Tools → «Helm line to download». Kubach работает с обоими и с системным
  `helm` любой из линий: на Helm 4.3.1 и 3.22.1 на minikube проверены repo add /
  update / remove и нативный поиск по индексу, `show values|readme`, install с
  `--dry-run=server --output json` и без, разбор `--debug`-прогресса (#382), upgrade
  из `oci://` реестра, rollback, нативные list и history, драйверы Secret и ConfigMap,
  uninstall, текст ошибки о недостающих CRD (`kubach-core/tests/helm_compat_cluster.rs`
  и прежние `helm_cluster`, `helm_live_cluster`). Различий, которые задевают Kubach,
  нет (формат хранения релизов `helm.sh/release.v1` тот же).
- Версия для скачивания — из `https://get.helm.sh/helm-latest-version` (Helm 4) и
  `helm3-latest-version` (Helm 3): строго `vX.Y.Z` своей мажорной линии, иначе ответ
  игнорируется. Ответ кэшируется в `<data_dir>/tools/helm-latest.json` (обе линии и
  время проверки) и спрашивается **не чаще раза в сутки** — только пока открыт
  Settings → Tools или при скачивании, — и по кнопке «Check for updates». После
  неудачной проверки автоматическая повторяется не раньше чем через час. Версия ниже
  прошитой не берётся (устаревший или подменённый ответ). В Settings → Tools —
  «Available: Helm X.Y.Z», когда проверяли, Update для скачанной старой версии или
  другой линии.
- Прошитая версия (`HELM4` = 4.3.1, `HELM3` = 3.22.1 в `kubach_core::tools::helm`,
  с SHA-256 архивов шести платформ, сверенными с `.sha256sum` на `get.helm.sh` и с
  примечаниями к релизам на GitHub) остаётся запасной и поднимается с релизами Kubach.
- Любая версия, кроме прошитой, ставится **только с валидной OpenPGP-подписью** ключом
  мейнтейнера Helm, зашитым в Kubach: Helm подписывает каждый файл релиза, `.asc`
  лежат в релизе на GitHub
  (`github.com/helm/helm/releases/download/v<ver>/<archive>.asc` и
  `<archive>.sha256sum.asc`; на `get.helm.sh` подписей нет). Проверяются обе подписи:
  `.sha256sum` (до скачивания архива) и самого архива (после, потоково по файлу), плюс
  совпадение SHA-256 архива с `.sha256sum`. Подписавший ключ должен быть основным
  ключом связки или её подписывающим подключом с валидной привязкой, не отозван и не
  истёк на момент подписи. Нет `.asc`, неизвестный ключ, неверная подпись — архив
  удаляется, не ставится. Редиректы (GitHub → `release-assets.githubusercontent.com`)
  — до 5, только `https`.
- Ключи — файл `KEYS` из `github.com/helm/helm` без изменений
  (`kubach-core/src/tools/helm-KEYS`, коммит `5638c35399464b6432ba81b92a341218991efa5c`),
  загружаются ключи с валидной самоподписью; список отпечатков зашит рядом
  (`HELM_KEY_FINGERPRINTS`), тест держит их в согласии. Релизы 4.3.1, 4.3.0, 4.1.0,
  3.22.1, 3.22.0, 3.20.0 и 3.19.0 подписаны
  ключом Scott Rigby `208D D36E D5BB 3745 A167 43A4 C7C6 FBB5 B91C 1155` — отпечаток
  сверен по `KEYS`, по примечаниям к релизам на GitHub («This release was signed with
  …»), по его Keybase (`r6by`, на который ссылаются примечания;
  helm.sh/docs/topics/provenance советует сверять ключи мейнтейнеров через Keybase) и
  по keys.openpgp.org. 4.2.3 подписан ключом Matthew Farina
  `672C 657B E06B 4B30 969C 4A57 4614 49C2 5E36 B98E` из того же `KEYS`. Новый ключ
  мейнтейнера появляется в Kubach только с обновлением `KEYS` в новом релизе Kubach;
  до тех пор релизы, подписанные им, не ставятся (откат, ниже).
- Откат: не удалось узнать версию (нет сети), скачать или проверить подпись
  актуальной — ставится прошитая версия своей линии по прошитому SHA-256, а
  пользователь видит, почему («Helm X was not installed: … Installed Helm Y pinned in
  Kubach instead»). Для прошитой версии подпись тоже проверяется, но её отсутствие не
  мешает установке — отмечается в статусе. Локальные ошибки (диск, права) отката не
  вызывают. Как проверена скачанная копия, пишется рядом с бинарём
  (`<ver>/verification.json`: SHA-256, «pinned», подписавший или причина) и
  показывается в Settings → Tools: «Signed by Scott Rigby <scott@r6by.com> (208D …)»
  или «Checked by the SHA-256 pinned in Kubach».
- Библиотека OpenPGP — `pgp` (rPGP 0.21, чистый Rust, без `bzip2`). Sequoia
  (`sequoia-openpgp` с `crypto-rust`) тяжелее: 168 зависимостей против 144, чистая
  сборка ~50 с против ~43 с, `target` 671 МБ против 413 МБ (opt-level 3, M-серия), а
  рукописный разбор пакетов поверх `rsa`/`ed25519-dalek` — лишний риск в коде
  проверки подписи. rPGP добавляет в дерево Kubach ~80 крейтов (RustCrypto-примитивы).
- Запросы к `get.helm.sh` (версия) и `github.com` (подписи) — то же исключение из
  ADR 0004, что и сама загрузка: анонимный `GET`, без данных пользователя; суточная
  проверка идёт, только когда пользователь смотрит на загрузку Helm.

### Чарты: репозитории, поиск, установка (#130)
- Экран Helm разделён на страницы Releases (всё прежнее) и Charts — отдельные пункты
  группы Helm в sidebar (#138), без вкладок. Обе страницы — один `HelmScreen`
  (общий баннер вызовов `helm`), состояние каждой сохраняется при переключении пунктов.
  После установки чарта экран просит workspace выбрать пункт Releases
  (`ShowHelmPage`) и открывает новый релиз.
- Список репозиториев и поиск по чартам — **нативно**, без бинаря `helm` и без сети
  (`kubach-core::helm::repo`): читаются `repositories.yaml` и закэшированные
  `<cache>/<name>-index.yaml` пользователя. Пути — по правилам Helm:
  `HELM_REPOSITORY_CONFIG` / `HELM_REPOSITORY_CACHE`, иначе `HELM_CONFIG_HOME` /
  `HELM_CACHE_HOME`, иначе `XDG_CONFIG_HOME` / `XDG_CACHE_HOME` + `helm`, иначе
  умолчания платформы (`~/Library/Preferences|Caches` на macOS, `%APPDATA%` и
  `%TEMP%` на Windows, `~/.config` и `~/.cache` на Linux). Из `repositories.yaml`
  берутся только имя и URL — логины, пароли и TLS-файлы не читаются. Неизменённый
  индекс (размер и mtime) повторно не разбирается.
- Поиск повторяет `helm search repo`: подстрока без учёта регистра в `repo/chart`,
  описании и ключевых словах; совпадения по имени выше; по умолчанию последняя
  стабильная версия, «All versions» — все версии, включая pre-release. Отличие:
  чарт, у которого есть только pre-release, показывается, а не скрывается.
- Через `helm` — то, что меняет состояние или требует рендера/загрузки чарта:
  `helm repo add <name> <url> [--username u --password-stdin]`, `helm repo update [name]`,
  `helm repo remove <name>` (с подтверждением), `helm show values|readme` для карточки
  чарта и дефолтных values, `helm install`. Репозитории — те же, что у `helm` в
  терминале. Пароль приватного репозитория идёт только в stdin (`--password-stdin`),
  не в аргументы и не в отображаемую команду; хранит его сам `helm` в
  `repositories.yaml`, как при добавлении из терминала.
- Install: `helm install <release> <chart> [--version v] --values - [--create-namespace]`
  с теми же `--kube-context`, `--kubeconfig`, `--namespace`, `HELM_DRIVER`, что и
  upgrade; values через stdin, стартуют с `helm show values`. Namespace выбирается из
  существующих или вводится новый; для namespace, которого нет в кластере,
  `--create-namespace` ставится всегда (без него install падает с
  `namespaces "…" not found`). Новый он или существующий, решает чистая функция
  `kubach-core::helm::target_namespace::decide` (#292): по загруженному списку
  namespace; пока список грузится, Preview и Install ждут (кнопки с индикатором),
  если флаг не отмечен вручную; если список недоступен (RBAC, ошибка) — точечный
  `GET namespace/<name>` (только метаданные): найден — флаг по галочке, 404 — флаг
  ставится всегда, отказ или ошибка — флаг по умолчанию включён с пометкой «не
  удалось проверить» и его можно снять (helm пропускает уже существующий namespace,
  но всё равно просит API-сервер его создать — без права create это отказ).
  Предпросмотр — `--dry-run=server --output json` —
  необязателен (#137): установить можно и без него, подтверждение — как у upgrade, и
  в нём сказано, был ли предпросмотр этого ввода. Проверено на Helm 3.22 и 4.2:
  server dry-run не создаёт namespace и не отправляет объекты в API-сервер, поэтому
  предпросмотр в новый namespace работает так же, как в существующий (и ошибки
  валидации объектов сервером не ловит). После установки открывается новый релиз.
- OCI (`oci://…`), путь или URL ставятся по ссылке без репозитория; `helm repo add`
  для `oci://` не предлагается.
- Поиск во внешних каталогах (Artifact Hub) не делается (ADR 0004).

### Иконки чартов и README (#167, #169)
- Charts показывают иконку чарта (`icon` из закэшированного `index.yaml`) в списке и
  карточке, Releases — из метаданных чарта, сохранённых в релизе (`chart.metadata.icon`
  того же декодированного Secret/ConfigMap, без вызова `helm`). Без иконки, пока она
  грузится и при ошибке — заглушка с первой буквой имени (цвета темы).
- README в карточке чарта рендерится как Markdown (`gpui_base::TextView`: заголовки,
  списки, таблицы, код); ссылки открываются в браузере, переключатель «Source»
  показывает исходник в редакторе. Картинки README (Markdown и HTML `<img>`) идут
  через тот же загрузчик, что иконки.
- **Это первые исходящие запросы не к кластеру и не к Helm-репозиторию, которые Kubach
  делает сам, без отдельного действия пользователя**: адрес картинки задаёт автор
  чарта, и это может быть любой хост. Решено делать так, потому что без иконок и
  картинок список чартов и README заметно хуже читаются, а запрос — обычный анонимный
  `GET` картинки, такой же, как при открытии README в браузере. Выключается
  настройкой **Settings → Tools → Helm → «Load chart icons»** (`helm.load_chart_icons`
  в `settings.toml`, по умолчанию включена). Выключена — Kubach не отправляет ни одного
  такого запроса и не читает кэш: вместо иконок заглушки, вместо картинок README их
  alt-текст; при выключении идущие загрузки прерываются.
- Ограничения загрузчика (`kubach_core::images`): только `http`/`https`, `GET` без
  cookies, логинов и заголовков авторизации (клиент — тот же `kube::Client`, что для
  загрузки `helm`, с прокси из окружения); до 5 редиректов; не больше 4 загрузок
  одновременно; таймауты — 10 с на соединение, 15 с на ожидание данных, 30 с на всю
  загрузку; ответ больше 4 МБ отбрасывается; сохраняется только PNG, JPEG, GIF, WebP
  или SVG (проверка по содержимому). Относительные адреса и `file:`/`data:` не
  загружаются. Грузится только видимое: строки таблицы, которые сейчас отрисованы, и
  блоки README, попавшие в окно.
- Размер в пикселях (#201): маленький файл может описывать огромную картинку
  (SVG с `width="20000"`, PNG с 100000×100000 в заголовке), а GPUI декодирует растр в
  полный размер, каждый кадр анимации, и растеризует SVG с масштабом ×2 — это
  гигабайты памяти. Поэтому перед сохранением в кэш и перед отдачей закэшированного
  файла в UI проверяется размер: PNG, JPEG, GIF, WebP — по заголовку, SVG — разбором
  через `usvg` (той же версии, что в GPUI) с учётом единиц и `viewBox`, плюс
  встроенные `data:`-картинки внутри SVG. Сторона — не больше 4096 пикселей (у SVG —
  итоговый размер растеризации, то есть не больше 2048 в единицах SVG), все кадры
  анимированного GIF/WebP вместе — не больше 4×4096² пикселей. Не прошла проверку —
  ошибка и заглушка с буквой; такой файл, оставшийся в кэше от старой версии,
  удаляется.
- Внешние ссылки в SVG (#229): GPUI рисует SVG стандартным резолвером `usvg`, который
  читает локальный файл по `<image href="/путь">` или `file://`, а SVG приходит со
  стороннего хоста. Поэтому SVG с внешней ссылкой на ресурс **отклоняется** (а не
  очищается: вырезать надёжно сложнее, чем отказать): `href`/`xlink:href` любого
  элемента (`<image>`, `<use>`, `<feImage>`…), кроме внутренних `#id` и `data:`;
  CSS `url(…)` не на `#id`/`data:` в `<style>` и атрибутах (с учётом комментариев и
  CSS-экранирования), `@import`, `<?xml-stylesheet?>`. Ссылки `<a href>` — не ресурсы
  и допустимы. XML разбирается тем же `roxmltree`, что в `usvg` (с DTD и внутренними
  сущностями, так что ссылка за сущностью тоже видна; внешние сущности не грузятся).
  Вложенные `data:`-SVG проверяются так же, а при проверке размера `usvg` ошибкой
  считается любая попытка обратиться к резолверу файлов. Проверка идёт перед
  сохранением в кэш и перед отдачей закэшированного файла, как для размеров;
  не прошедший файл из кэша удаляется.
- Адреса (#201): адрес картинки задаёт автор чарта, поэтому загрузчик не ходит на
  машину и в сеть пользователя. Запрещены loopback, private (RFC 1918, `fc00::/7`),
  link-local (в том числе `169.254.169.254`, метаданные облака), unspecified,
  multicast, broadcast, CGNAT и прочие служебные диапазоны, также в виде IPv6 со
  встроенным IPv4 (`::ffff:…`, NAT64, 6to4). Имя хоста резолвится самим загрузчиком,
  проверяется **каждый** адрес (хоть один запрещённый — отказ), и соединение идёт к
  проверенному адресу, а не к имени, так что повторный резолв не подменит его (DNS
  rebinding); TLS-сертификат при этом проверяется по имени. То же — на каждом
  редиректе, а редирект с `https` на `http` запрещён. Через прокси из окружения имя
  отдаётся прокси: локально резолвящееся имя проверяется так же, а нерезолвящееся
  (сеть только через прокси) остаётся на совести прокси — сам прокси на loopback
  разрешён, это настройка пользователя.
- Кэш на диске — `<config dir>/cache/images/<sha256 адреса>` (`KUBACH_CONFIG_DIR`
  переопределяет папку), запись атомарная. Скачанное повторно не запрашивается;
  ошибки запоминаются до перезапуска или до повторного включения настройки. Кэш не
  чистится автоматически — его можно удалить вручную.

## Последствия
- Изменения ведут себя ровно как в CLI пользователя, история релиза не повреждается
  несовместимой записью.
- Нет 50+ МБ бинаря на платформу в дистрибутиве. Скачивается актуальная версия с
  подписью мейнтейнера; прошитая — запасная: при её подъёме нужно обновить хэши для
  всех платформ (`.sha256sum` с `get.helm.sh` и примечания к релизу на GitHub), при
  смене ключей мейнтейнеров — `helm-KEYS` и `HELM_KEY_FINGERPRINTS`.
- Нужна обёртка запуска процесса (таймауты, отмена, вывод ошибок в UI); MCP (#12)
  получает доступ к изменениям только через неё и с правами по ADR 0005.
- Нативный rollback/uninstall можно вернуть новым ADR, если зависимость от CLI станет проблемой.
- Предпросмотр upgrade показывает рендер на момент dry-run: если релиз изменился
  между предпросмотром и применением, UI предупреждает, но `helm upgrade` всё равно
  рендерит заново. Временная папка с чартом может содержать секреты из дефолтных
  values чарта — она живёт только на время вызова.

## Helm для MCP-агента (#418)
Агент меняет релизы тем же `helm`, что и экраны (тот же выбор бинаря, те же `HelmCommand` с
`--` перед позиционными аргументами, values через stdin, фазы `--debug`). Отличия — в
[ADR 0005, «Helm через агента»](0005-mcp-permissions.md#helm-через-агента-418): идентичность
namespace сессии вместо учётных данных пользователя (токен временного SA через
`HELM_KUBETOKEN` и kubeconfig без учётных данных — `HelmTarget::secret_env`, не попадает в
аргументы и `Debug`), превью и подтверждение каждого изменения, чарты только из добавленных
репозиториев или разрешённого `oci://`.
