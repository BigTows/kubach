# 0015 — Локальный терминал: временный kubeconfig с текущим контекстом

Статус: принято

## Контекст
Встроенный терминал умел только exec в контейнер и debug-контейнер. Нужна вкладка с
локальной оболочкой пользователя, в которой `kubectl`, `helm`, `k9s` работают с тем же
контекстом и namespace, что открыты в окне Kubach (#319). Переключать
`current-context` в общем `~/.kube/config` нельзя: это меняет поведение всех остальных
терминалов пользователя и гонится с ними. Кластеры из vault (ADR 0008) вообще не
лежат в файлах: их креды есть только в памяти разблокированного хранилища.

## Решение
- **PTY.** `kubach_core::pty`: на Windows ConPTY через `portable-pty` (из wezterm),
  на Unix — свой PTY и `posix_spawn` (см. ниже «Запуск без fork»).
  `alacritty_terminal::tty` не подошёл: без его `EventLoop` (которому нужен
  собственный `Term`, а у нас `Term` живёт в `TerminalView`) на Windows неблокирующее
  чтение пришлось бы писать самим. Вывод читается, ввод пишется в своих потоках;
  `PtyHandle` при удалении шлёт `SIGHUP` группе процессов оболочки (она лидер своей
  сессии), через секунду — `SIGKILL`; на Windows процесс завершается. Оболочка —
  `$SHELL -l` в домашней папке (на Windows `pwsh`, `powershell` или `%COMSPEC%`), с
  окружением процесса Kubach (то есть уже с окружением login shell, ADR 0013) плюс
  `TERM=xterm-256color`, `COLORTERM`, `TERM_PROGRAM=Kubach` и `KUBECONFIG`.
- **Запуск без fork (Unix, #385).** `portable-pty` делает `fork` многопоточного
  приложения и в `pre_exec` выполняет в дочернем процессе Rust-код (`setsid`,
  `TIOCSCTTY`, закрытие дескрипторов через `read_dir` по `/dev/fd` с аллокациями) —
  после `fork` это может зависнуть или упасть на замке или аллокаторе, захваченном
  другим потоком (тот же класс сбоя, что `os_once_t is corrupt` в #375). Поэтому на
  Unix PTY открывается через `openpty` (обе стороны сразу close-on-exec), а оболочка
  запускается `posix_spawn` (общие обёртки — `kubach_core::spawn`, их же использует
  захват окружения login shell): `POSIX_SPAWN_SETSID`, пустая маска сигналов и
  действие по умолчанию для `SIGPIPE`, `SIGINT`, `SIGTSTP` и др., на macOS ещё
  `POSIX_SPAWN_CLOEXEC_DEFAULT`. В file actions терминальная сторона открывается
  **по пути** (`TIOCPTYGNAME` на macOS, `ptsname_r` на Linux) как stdin без
  `O_NOCTTY` и дублируется в stdout/stderr, затем `chdir`. Так в процессе Kubach
  никакого нашего кода в дочернем процессе нет (macOS: один syscall; glibc/musl:
  `clone(CLONE_VM|CLONE_VFORK)` без atfork-обработчиков).
  - *Управляющий терминал.* Лидер сессии без управляющего терминала, открывший TTY
    без `O_NOCTTY`, получает его управляющим: на Linux это поведение `open`, а
    glibc и musl делают `setsid` до file actions; на macOS (XNU) `posix_spawn` с
    `POSIX_SPAWN_SETSID` даёт тот же результат — проверено тестами: `tpgid == pgid
    == pid`, `/dev/tty` открывается, `Ctrl-C` прерывает группу переднего плана,
    `Ctrl-Z` в `sh -i` останавливает задание, `stty size` видит resize. Поэтому
    ни `TIOCSCTTY`, ни вспомогательный exec-процесс (`--pty-helper`,
    `/usr/bin/script`) не нужны: они добавили бы лишний процесс в цепочку и
    зависимость от внешней утилиты.
  - *Читатель запускается до процесса.* macOS выбрасывает вывод, оставшийся в
    очереди PTY, если при последнем закрытии терминальной стороны его никто не
    прочитал за ~0,6 с (`ptsclose`); короткоживущий процесс под нагрузкой терял
    весь вывод, пока поток чтения не успевал стартовать. Поток чтения создаётся
    сразу после открытия PTY, до `posix_spawn`.
  - *Компромисс на Linux.* `POSIX_SPAWN_CLOEXEC_DEFAULT` там нет, а
    `posix_spawn_file_actions_addclosefrom_np` требует glibc 2.34: в оболочку
    попадают дескрипторы, открытые сторонним кодом без close-on-exec. Rust std,
    tokio и наши дескрипторы всегда close-on-exec, так что это редкость; закрывать
    их «вручную» в дочернем процессе — ровно то, от чего мы ушли.
- **Временный kubeconfig.** При открытии вкладки (и при перезапуске оболочки) из
  объединённого kubeconfig Kubach (`Contexts`, куда входят и конфиги разблокированного
  vault) берётся один контекст — активный — с его кластером и пользователем;
  `current-context` указывает на него, `namespace` контекста заменяется namespace,
  выбранным в окне (если выбран ровно один; иначе — namespace контекста по
  умолчанию). Exec-плагины, токены, сертификаты копируются как есть; креды vault
  материализуются в файл. `KUBECONFIG=<файл>` передаётся только дочернему процессу
  (не `set_var`), глобальный `~/.kube/config` не меняется.
- **Где и с какими правами.** `<config dir>/run/kubeconfig/terminal-<pid>-<n>.yaml`
  (`KUBACH_CONFIG_DIR` учитывается). Каталог создаётся `0700`, файл — сразу `0600`
  (`O_CREAT|O_EXCL` с режимом, без окна, когда он читаем другими); на Windows — DACL
  только для текущего пользователя до записи содержимого. Не общая `/tmp`: там чужие
  процессы видят имена и могут подложить файл или симлинк заранее. Не `cache/`: его
  удаляет «Clear cache» при открытых вкладках.
- **Удаление.** Файл удаляется, когда оболочка завершилась, при перезапуске, при
  закрытии вкладки (`TempKubeconfig` удаляет файл в `Drop`) и при выходе из Kubach
  (`on_app_quit` удаляет все файлы своего pid). Файлы, оставшиеся после падения или
  `kill`, удаляются при следующем старте: файл, чей pid уже не жив, — сирота.

## Модель угроз
- Защищаемся от других локальных пользователей и процессов других учётных записей:
  права `0600`/`0700` и DACL, каталог в профиле пользователя.
- Не защищаемся от процессов того же пользователя: они и так читают `~/.kube/config`,
  Keychain по запросу и память Kubach. Оболочка во вкладке по определению получает
  креды контекста — это и есть цель функции.
- Креды vault, которые раньше были только в памяти, на время жизни вкладки лежат на
  диске (в профиле, `0600`). Это осознанный компромисс; файл содержит только один
  контекст, а не всё хранилище. Блокировка vault уже открытый файл не удаляет:
  оболочка продолжает работать, пока вкладка открыта.
- После `kill -9` или падения файл живёт до следующего старта Kubach. Шифрование
  диска (FileVault, BitLocker) — ответственность системы.
- Exec-плагины с относительным путём к команде разрешаются kubectl относительно
  каталога временного файла, а не исходного kubeconfig; такие конфиги редки, при
  необходимости путь в исходном файле делается абсолютным.

## Последствия
- Несколько вкладок — несколько файлов и независимых оболочек; смена контекста в окне
  открытые вкладки не трогает (заголовок «Terminal — контекст/namespace» показывает,
  с чем вкладка открыта).
- Системный терминал («Open in Terminal») пока не открывается: его жизнь не связана
  с вкладкой, и непонятно, кто удалит файл с кредами. Отдельная задача.
- `portable-pty` (с `nix`, `serial2`, `filedescriptor`) теперь зависимость только
  для Windows.
