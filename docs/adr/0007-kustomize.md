# 0007 — Kustomize: сборка через `kustomize` или `kubectl kustomize`

Статус: принято

## Контекст
Kubach показывает результат сборки kustomization-директории и его отличия от кластера (#15).
Kustomize — большая Go-библиотека (`kyaml`): overlays, патчи (strategic merge с учётом
OpenAPI-схем, JSON 6902), генераторы с хешем имени, replacements, components, удалённые
базы (`git`, HTTP), `helmCharts`, плагины/KRM-функции. Нативной реализации на Rust нет,
повторить поведение один в один нереально, а расхождение с тем, что потом применит
Flux/Argo CD или `kubectl apply -k`, хуже отсутствия функции.

## Решение
- Сборка — вызовом бинаря пользователя (как `helm` в ADR 0006): `kustomize build <dir>`,
  если `kustomize` есть в `PATH`, иначе `kubectl kustomize <dir>` (встроенный, обычно
  старее). Путь к бинарю будет настраиваться (#41). Kubach ничего не бандлит.
- Сборка локальная: без доступа к кластеру, ничего не применяется. Таймаут, процесс
  убивается при отмене; stderr при успехе отдаётся как предупреждения.
- Вывод разбирается `apply::yaml::parse`; diff с кластером — `apply::resolve` + GET живых
  объектов + `apply::diff` (только поля из манифеста, без статуса и дефолтов сервера).
  Точный предпросмотр с дефолтами и вебхуками — server-side dry-run из `apply`.
- Нет ни `kustomize`, ни `kubectl` — понятная ошибка (`NoTool`), просмотр остального работает.

## Последствия
- Результат совпадает с тем, что собирает CLI пользователя, включая его версию kustomize.
- Нужен внешний процесс; при запуске из Finder/Dock `PATH` берётся из login-shell (`shell_env`).
- `--enable-helm` требует `helm` в `PATH`; удалённые базы требуют сети и `git`.
- Нативную сборку можно вернуть отдельным ADR, если появится зрелая Rust-реализация.
