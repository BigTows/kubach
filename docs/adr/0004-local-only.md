# 0004 — Только локальная работа, без агента в кластере

Статус: принято

## Контекст
Можно устанавливать в кластер агента или работать только с API с машины пользователя.

## Решение
Kubach работает только локально и использует права из kubeconfig пользователя.
В кластер ничего не устанавливается.

## Последствия
- Не нужны права на установку и поддержка компонентов в кластере.
- Вся агрегация и кэш — на стороне клиента (list+watch), нагрузка на API растёт с числом открытых ресурсов.
- Возможности, требующие серверной части (история метрик и т. п.), вне охвата.
- MCP (#12) работает локально.
  _Обновлено (#208): механизм прав выбран в [ADR 0005](0005-mcp-permissions.md); MCP живёт в
  крейте `kubach-mcp` и ходит в API своим клиентом под идентичностью сессии, а не поверх
  кэша приложения (см. [архитектуру](../architecture.md))._
- Исключение: загрузка внешних инструментов (сейчас `helm`) с официального сайта по
  явному действию пользователя, в папку данных Kubach, с проверкой SHA-256 (ADR 0006).
  _Обновлено (#38): так же по явному действию скачиваются CLI облаков для импорта
  кластеров — `gcloud`, `yc`, `aws` — с сайтов производителей, с проверкой там, где
  производитель её публикует (SHA-256 Google, PGP-подпись и подпись Apple пакета AWS;
  для `yc` Yandex ничего не публикует — только HTTPS), см. [ADR 0019](0019-cloud-import.md).
  Сами списки кластеров запрашивает CLI пользователя под его логином; Kubach токенов облака
  не хранит._
- Исключение: иконки чартов и картинки README по адресам из чартов, выключаются
  настройкой «Load chart icons» (ADR 0006).
- Исключение (#318): временные объекты по явному действию пользователя, которые Kubach
  сам и удаляет: ephemeral debug-контейнер и привилегированный под Shell на ноде
  (лейблы `app.kubernetes.io/managed-by: kubach`, `kubach.dev/node-shell`; удаляется при
  закрытии вкладки и выходе, осиротевшие после сбоя — при следующем подключении к контексту).
  _Обновлено (#351): кластером могут пользоваться несколько экземпляров Kubach (другой процесс,
  пользователь или машина), поэтому под Shell на ноде помечен владельцем: аннотации
  `kubach.dev/owner-install` (случайный UUID установки из файла `install-id` в каталоге
  конфигурации, учитывает `KUBACH_CONFIG_DIR`), `kubach.dev/owner-pid`, `kubach.dev/owner-host`
  и лейбл `kubach.dev/owner` (короткий хеш id установки). Пока вкладка открыта, она раз в 30 с
  обновляет аннотацию `kubach.dev/heartbeat` (merge patch). Подчистка при подключении удаляет
  без подтверждения только: (а) свои осиротевшие поды — та же установка и хост, а процесс
  с pid из аннотации не запущен (или это наш процесс, но вкладки с этим подом нет дольше
  2 минут); это мусор самого Kubach; (б) чужие поды, чей heartbeat (без него — время создания)
  старше 15 минут. Порог «протух» — 5 минут, но удаление чужого без явного клика допускается
  только при сильно протухшем heartbeat (≥ 15 минут: с запасом на пропуски, сон ноутбука и
  расхождение часов); между 5 и 15 минутами под пропускается. Живой чужой под не удаляется
  никогда. Без права `patch pods` heartbeat не обновляется, и через 15 минут после создания
  такой под может удалить другой экземпляр._
