# 0005 — Права MCP-агента на namespace

Статус: принято

## Контекст
Kubach выступает MCP-сервером (#12): AI-агент подключается к нему и работает с кластером
в рамках, которые пользователь выбрал в UI: один namespace и профиль. С #401 namespace не
выбирается заранее: агент называет его сам, а пользователь разрешает чтение при первом
обращении (см. «Namespace по запросу»).

| Профиль | Что разрешено |
|---------|---------------|
| read-only | `get`/`list`/`watch` ресурсов namespace, events. Без Secrets |
| debug | read-only, плюс `pods/log` и `pods/exec` |
| deploy | read-only, плюс apply (SSA), rollout, scale и delete в namespace |

Ограничения:
- [ADR 0004](0004-local-only.md): работаем локально с правами из kubeconfig, в кластер
  ничего не устанавливается.
- Агент не получает учётных данных: он видит только MCP-tools, а запросы к API делает Kubach.
  Поэтому вопрос не в том, «какой токен отдать агенту», а в том, **под какой идентичностью
  Kubach выполняет вызовы агента** и кто гарантирует границу namespace: сам Kubach или ещё и
  API-сервер.
- Модель угроз: агент мог получить prompt injection (из логов, YAML, описаний ресурсов) и
  пытается выйти за namespace или профиль. Вторая угроза — ошибка в коде Kubach, из-за которой
  проверка пропускает лишний вызов.
- Пользователи — обычные разработчики. На managed-кластерах (EKS/GKE/AKS) у них чаще всего
  `edit` или `admin` в своих namespace и нет прав на уровне кластера.

Что даёт встроенная RBAC-модель (из [bootstrap-политик](https://github.com/kubernetes/kubernetes/blob/master/plugin/pkg/auth/authorizer/rbac/bootstrappolicy/testdata/cluster-roles.yaml)
и [user-facing roles](https://kubernetes.io/docs/reference/access-authn-authz/rbac/#user-facing-roles)):

| Право | `edit` в ns | `admin` в ns |
|-------|:-----------:|:------------:|
| create `serviceaccounts` | да | да |
| create `serviceaccounts/token` (TokenRequest) | да | да |
| `impersonate` на `serviceaccounts` namespace | да | да |
| create `roles` / `rolebindings` | **нет** | да |
| `impersonate` на `users` / `groups` | нет | нет |

## Рассмотренные варианты

### 1. Impersonation заранее подготовленной идентичности
Kubach ходит в API с учётными данными пользователя и заголовками `Impersonate-User` /
`Impersonate-Group` (и `Impersonate-Extra-kubach.io/session: <id>`) от имени идентичности
вроде `kubach:mcp:<ns>:<profile>`. RBAC этой идентичности заранее создаёт администратор
([документация](https://kubernetes.io/docs/reference/access-authn-authz/authentication/#user-impersonation)).

- **Права пользователя**: `impersonate` на `users`/`groups` (кластерный ресурс, его нельзя
  выдать только в namespace) и, для extra, на `userextras/<key>`. Это фактически права
  администратора: умеющий impersonate произвольную группу может стать `system:masters`,
  если `resourceNames` не ограничены
  ([RBAC good practices](https://kubernetes.io/docs/concepts/security/rbac-good-practices/#impersonate)).
  Плюс кто-то должен один раз создать Role/RoleBinding для каждой пары namespace и профиль.
- **Managed-кластеры**: механизм поддерживается везде, но в типичных developer-ролях
  (namespace-scoped access policies EKS, роли AKS «RBAC Writer/Admin», RoleBinding на
  `edit`/`admin`) impersonate пользователей и групп нет. Нужна платформенная команда.
- **Безопасность**: граница проверяется API-сервером. При impersonation проверяются только права
  идентичности, и поэтому RBAC идентичности должен быть узким. В Kubernetes 1.35 появилась
  alpha-версия [constrained impersonation (KEP-5284)](https://www.kubernetes.dev/resources/keps/5284/),
  с ней можно запретить делать через impersonation то, что не может сам пользователь
  (`impersonate:user-info` + `impersonate-on:user-info:<verb>`). В managed-кластерах её пока нет.
- **Аудит**: в audit-событии есть и `user` (реальный пользователь), и `impersonatedUser`
  (с extra `kubach.io/session`). Это лучший след из всех вариантов.
- **Очистка**: в кластере ничего не создаётся, сессия заканчивается, когда Kubach перестаёт
  слать заголовки. Сбоев с «осиротевшими» объектами нет.
- **kube-rs**: `Config.auth_info.impersonate` / `impersonate_groups` уже есть.
  `Impersonate-Extra-*` придётся добавить своим tower-слоем. Сложность низкая.
- **UX**: если администратор настроил RBAC, пользователь выбирает namespace и профиль. Без
  настройки варианта нет. Kubach может показать готовый YAML для администратора.

Отдельно: `edit` разрешает impersonate ServiceAccount своего namespace. Но у существующих SA
либо нет нужных прав, либо они слишком широкие (SA приложения). Без своего SA с узкой Role это
не помогает, поэтому подвариант отброшен.

### 2. Временные ServiceAccount + Role + RoleBinding, токен через TokenRequest
На старте сессии Kubach создаёт в namespace `ServiceAccount kubach-mcp-<id>`, `Role` с
правилами профиля и `RoleBinding`. Затем получает токен через
[TokenRequest](https://kubernetes.io/docs/reference/kubernetes-api/authentication-resources/token-request-v1/)
(`expirationSeconds` не меньше 600 с, API-сервер может урезать) и делает отдельный клиент с
этим bearer-токеном. Токен хранится только в памяти и обновляется до истечения.

- **Права пользователя**: create/delete на `serviceaccounts`, `roles`, `rolebindings` и create
  на `serviceaccounts/token` в namespace. Из-за
  [защиты от эскалации](https://kubernetes.io/docs/reference/access-authn-authz/rbac/#privilege-escalation-prevention-and-bootstrapping)
  Role создаётся, только если у пользователя уже есть все права из неё (или `escalate`), а
  RoleBinding — только если есть права роли (или `bind`). Агент не получит больше, чем есть у
  пользователя. Профиль debug недоступен тому, у кого нет `pods/exec`. По сути нужен `admin` в
  namespace: `edit` не хватает, потому что он не создаёт Role/RoleBinding.
- **Managed-кластеры**: работает везде, где пользователь — admin namespace (EKS
  `AmazonEKSAdminPolicy` с namespace-scope, AKS «RBAC Admin» на namespace, RoleBinding на
  `admin` в GKE). SA-токены — штатный механизм аутентификации Kubernetes, их принимает API-сервер
  managed-кластеров (проверить на AKS с отключёнными local accounts).
- **Безопасность**: граница проверяется API-сервером под отдельной идентичностью. Даже если в
  Kubach ошибка, клиент сессии физически не может читать другой namespace.
- **Аудит**: вызовы агента видны как `system:serviceaccount:<ns>:kubach-mcp-<id>`, а создание
  SA и Role — от имени пользователя. Связь через аннотацию `kubach.io/created-by` и User-Agent.
  Связь слабее, чем `impersonatedUser`, но различима.
- **Очистка и сбои**:
  - Role и RoleBinding получают `ownerReferences` на SA, тогда удаление SA каскадно удаляет
    всё через GC. Удаление SA сразу инвалидирует его bound-токены
    ([service accounts](https://kubernetes.io/docs/reference/access-authn-authz/service-accounts-admin/#bound-service-account-token-volume)).
  - Нативного TTL у SA нет. Метки `app.kubernetes.io/managed-by=kubach`, `kubach.io/session`
    и аннотация `kubach.io/expires-at`. При закрытии сессии и по TTL Kubach удаляет SA.
  - Если приложение упало, токен сам истекает через `expirationSeconds`, а объекты остаются.
    При следующем подключении к контексту Kubach удаляет просроченные объекты по меткам. Пока
    осиротевшая RoleBinding живёт, любой с `serviceaccounts/token` в namespace (`edit`) может
    выпустить себе токен с правами профиля. Обычно это не больше, чем у него уже есть, но
    риск ненулевой.
  - Если нет сети или прав на удаление, объекты остаются, и UI должен это показать.
- **Отношение к ADR 0004**: это не установка компонента, а временные объекты сессии. Но
  требование «в кластер ничего не устанавливается» смягчается, и решение за владельцем
  проекта.
- **kube-rs**: `Api::<ServiceAccount>::create_token_request` есть в kube-client 4.2. Нужны
  второй `Client` (тот же `cluster_url` и CA, `auth_info.token`), обновление токена, очистка
  и sweep. Сложность средняя.
- **UX**: пользователь выбирает namespace, профиль и TTL и жмёт «Начать сессию». Kubach через
  `SelfSubjectAccessReview` заранее проверяет, хватает ли прав, и объясняет, чего не хватает.

### 3. Только проверки на стороне клиента
Kubach выполняет вызовы агента с учётными данными пользователя, а MCP-слой проверяет каждый
вызов: namespace из allowlist сессии, ресурс и verb из профиля, запрет Secrets.
[`SelfSubjectAccessReview`](https://kubernetes.io/docs/reference/access-authn-authz/authorization/#checking-api-access)
используется только для того, чтобы не предлагать недоступное.

- **Права пользователя**: никаких дополнительных. Работает на любом кластере.
- **Безопасность**: граница держится только на коде Kubach. Агент не может сам обойти
  проверку, у него нет кредов. Но любая ошибка в разборе (namespace в URL, `--all-namespaces`,
  кластерные ресурсы, поле `namespace` внутри манифеста apply, cross-namespace ссылки)
  выполнится с полными правами пользователя. SSAR проверяет права пользователя, а не профиля,
  и потому ничего не ограничивает.
- **Аудит**: в audit-логе API-сервера вызовы агента неотличимы от действий человека, кроме
  User-Agent (`kubach-mcp/<версия> session/<id>`), который пишется в поле `userAgent`
  ([auditing](https://kubernetes.io/docs/tasks/debug/debug-cluster/audit/)). Полный след
  остаётся только в локальном журнале Kubach.
- **Очистка**: не нужна, сессия — это состояние в памяти.
- **kube-rs**: тот же клиент и кэш. Вся сложность в policy-слое и его тестах. Сложность
  низкая или средняя.
- **UX**: самый простой, но нужно честно показывать, что граница только на стороне Kubach.

### 4. Гибрид: клиентская политика всегда, серверная идентичность, когда возможно
Клиентская политика из варианта 3 — **основной** фильтр для каждой сессии. Поверх неё, если
позволяют права, Kubach выполняет вызовы агента под отдельной идентичностью (вариант 1 или 2)
как **вторую линию защиты**. Уровень защиты сессии виден в UI.

## Сравнение

| Критерий | 1. Impersonation | 2. Временный SA | 3. Только клиент | 4. Гибрид |
|----------|------------------|-----------------|------------------|-----------|
| Права пользователя | `impersonate` users/groups (уровень кластера) + RBAC от администратора | `admin` в namespace (SA, Role, RoleBinding, token) | никаких | любые; уровень защиты зависит от прав |
| Типичный разработчик на EKS/GKE/AKS | обычно нет | да, если admin namespace; с `edit` — нет | да | да |
| Кто держит границу namespace | API-сервер | API-сервер | только Kubach | Kubach + API-сервер (если доступно) |
| Ошибка в Kubach при prompt injection | ограничена RBAC идентичности | ограничена Role сессии | выполнится с правами пользователя | 1 или 2, иначе 3 |
| След в audit API-сервера | `user` + `impersonatedUser` + extra | отдельный SA-пользователь | только `userAgent` | по режиму |
| Объекты в кластере | нет | временные, с TTL | нет | по режиму |
| Сбой или падение Kubach | ничего не остаётся | осиротевшие объекты до sweep, токен истекает | ничего | по режиму |
| Отзыв доступа | сразу (перестать слать заголовки) | удаление SA сразу инвалидирует токен | сразу | сразу |
| Сложность в kube-rs | низкая (+ свой слой для extra) | средняя | низкая/средняя (policy) | средняя/высокая |
| Совместимость с ADR 0004 | полная | смягчение («временные объекты») | полная | по режиму |

## Решение

**Вариант 4, гибрид.** Режим выбирается автоматически при старте сессии:

1. **Клиентская политика — всегда и первой.** Каждый MCP-вызов проходит policy-слой:
   namespace сессии зафиксирован (агент не передаёт его, а если передаёт, должен совпасть),
   ресурсы и verbs — по профилю, кластерные ресурсы и `--all-namespaces` запрещены, поле
   `metadata.namespace` в манифестах принудительно совпадает с сессией. Этот слой работает на
   любом кластере и задаёт поведение независимо от режима.
2. **Серверная идентичность — если доступна**, в таком порядке:
   - **impersonation**, если для контекста настроена идентичность (администратор создал RBAC)
     и SSAR подтверждает `impersonate`. Ничего не создаётся;
   - иначе **временный SA**, если SSAR подтверждает права на SA, Role, RoleBinding и
     `serviceaccounts/token` в namespace;
   - иначе **только клиент**. UI явно помечает сессию «граница только в Kubach», а для
     профилей debug и deploy требует подтверждения каждого мутирующего вызова без
     «запомнить решение».
3. Агент никогда не получает токен или kubeconfig. Токены сессии живут только в памяти.

Почему так: варианты 1 и 2 по отдельности недоступны значительной части пользователей
(impersonate есть почти только у администраторов, создавать Role может только admin
namespace), а вариант 3 по отдельности не защищает от ошибок в Kubach. Гибрид работает везде
и даёт серверную гарантию там, где её можно получить.

### Как с этим сочетаются остальные требования #12
- **Human-in-the-loop.** Мутирующие вызовы (apply, delete, scale, rollout restart, exec)
  ставятся в очередь подтверждения в UI. Для apply сначала выполняется server-side apply с
  `dryRun=All` **под идентичностью сессии**, и пользователь видит diff и ошибки RBAC. Exec
  показывает точную команду, контейнер и под. Подтверждение не расширяет права: если вызов не
  проходит policy или RBAC сессии, кнопки «разрешить» нет.
- **Secrets.** Профили не включают `secrets` ни в Role, ни в policy. Если Secret всё же
  попадает в ответ (например, в `describe` или в списке ссылок), Kubach оставляет ключи и
  размер, а значения заменяет на `***`. Также вырезается аннотация
  `kubectl.kubernetes.io/last-applied-configuration`, в которой бывают данные Secret. В выводе
  логов и exec маскируются JWT, PEM-ключи и строки вида `password=` (best-effort, не гарантия).
  С #227 метаданные, проверки и раскрытие одного Secret — отдельные инструменты по настройке
  контекста, см. «Права по запросу».
- **Учётные данные вне Secrets (#193).** Объект, который видит агент, маскируется структурно,
  а не регулярками по тексту: в YAML `name` и `value` переменной окружения стоят на разных
  строках, и текстовый шаблон их не связывает. По имени ключа (`kubach_core::secrets::mask::
  is_sensitive_name`: части имени `PASS`, `PASSWORD`, `SECRET`, `TOKEN`, `KEY`, `AUTH`,
  `CRED`, `DSN`, `PRIVATE`, `CONN_STR`, … без учёта регистра, с границами по `_`, `-`, `.`,
  `/` и camelCase) значение заменяется на `*** (N bytes)` в `env[].value` любого шаблона пода
  (Pod, Deployment, StatefulSet, DaemonSet, ReplicaSet, Job, CronJob, `data` у
  ControllerRevision, CRD), в `data`/`binaryData` ConfigMap и в аннотациях (кроме
  last-applied, которая вырезается целиком). Обход — `mask_named_values` в core, чтобы им же
  пользовался UI; плейсхолдер с размером остаётся в MCP. Шаблон имени — эвристика: значение
  под безобидным именем (`DB_URL` с паролем внутри) закрывает только маскирование текста.
- **Локальный аудит.** JSONL в каталоге данных приложения: время, сессия, MCP-клиент, tool,
  аргументы (замаскированные), решение (policy / пользователь / API), идентичность
  (user, impersonated или SA), код ответа и длительность. Корреляция с audit API-сервера —
  через `Impersonate-Extra-kubach.io/session`, имя SA и User-Agent `kubach-mcp/<версия>
  session/<id>`. Журнал ведётся во всех режимах. В режиме «только клиент» это единственное
  место, где видно, что вызов сделал агент. Манифест `apply_manifest` перед записью
  разбирается (все документы) и проходит то же маскирование объектов, что и ответы агенту,
  поэтому значения `data`/`stringData` Secret в журнал не попадают ни как есть, ни в base64.
  Если YAML не разбирается, вместо текста пишутся только kind/name документов и размер
  (#193). Остальные строки аргументов маскируются как текст.
- **TTL и отзыв.** TTL сессии выбирается в UI. При истечении, закрытии сессии или выходе из
  приложения policy отклоняет вызовы, impersonation-клиент уничтожается, а временный SA
  удаляется. После падения — sweep по меткам при следующем подключении.

## Последствия
- Policy-слой — обязательная, тщательно тестируемая часть MCP-крейта, а не «дополнение». Его
  нужно покрыть тестами на обход namespace (URL, поля манифеста, ownerRef, cross-namespace
  ссылки).
- Серверная граница реальна только при чтении через идентичность сессии. Если MCP читает из
  общего кэша пользователя (как сейчас нарисовано в [architecture.md](../architecture.md)),
  чтение защищено только policy. Поэтому кэш должен уметь держать namespace-scoped reflector'ы
  с отдельным `Client` сессии, либо надо принять, что чтения проверяются только на клиенте
  (см. вопросы).
- «Namespace-scoped» не означает изоляцию от кластера. Exec (debug) — это произвольный код в
  контейнере: агент может прочитать токен SA пода и обратиться к API в обход Kubach.
  Apply (deploy) может создать под с любым SA namespace и получить его права. Поэтому exec и
  apply всегда идут через подтверждение, а policy deploy запрещает менять `serviceAccountName`,
  `hostPath`, `privileged` без отдельного явного подтверждения. С #190 так же помечаются
  ссылки на Secrets и токены ServiceAccount, а логи подов, которые агент сам создал или
  изменил, читаются только после подтверждения (см. «Secrets через поды и allowlist kind'ов»).
- Режим сессии виден пользователю. Это добавляет сложности в UI, но честно показывает,
  от чего защищает Kubach.
- Если выбран временный SA, ADR 0004 нужно уточнить: «постоянно ничего не устанавливается;
  допускаются временные объекты сессии с TTL и метками».
- Когда constrained impersonation (KEP-5284) появится в managed-кластерах, вариант 1 станет
  безопаснее для администраторов, и его можно будет предложить им как основной.

## Настройки безопасности контекста
Что разрешено агенту, решает не ADR, а пользователь: в окне настроек (#41) есть раздел
«Безопасность», он задаётся **отдельно для каждого контекста** (#39). Для нового контекста
действуют строгие значения по умолчанию, а для своих dev-кластеров (например, `minikube`)
пользователь может разрешить больше.

С #15 таблица ниже — история: настройки агента, кроме «Доступ AI-агента», заменены минимальным
доступом (см. «Минимальный доступ вместо потолка (#15)»).

| Настройка | Варианты | По умолчанию |
|-----------|----------|--------------|
| Доступ AI-агента (MCP) | выключен / включён | выключен; с #9 — включён (см. ниже) |
| Максимальный профиль | read-only / debug / deploy; с #227 — потолок прав по запросу; с #417 сверх него агент может попросить повысить потолок (см. «Повышение потолка по запросу») | read-only |
| Временные объекты в кластере (SA + Role + RoleBinding на сессию) | запрещены / разрешены; с #227 Role сессии патчится при каждой выдаче и отзыве права | запрещены |
| Изменения (deploy) | только dry-run и diff / применять после подтверждения (с #230 — и запись Secrets через пользователя) | только dry-run |
| Exec | запрещён / разовые команды с подтверждением / интерактивный shell | запрещён |
| TTL сессии («Session length») | до 8 ч; права сгорают с сессией; с #401 — длина HTTP-сессии без отдельного выбора, у `kubach mcp` по умолчанию 30 мин в пределах этой настройки | 30 мин |

| Скрывать значения Secrets (для человека, #96) | вкл / выкл; если вкл, агенту максимум «метаданные и проверки» | вкл |
| Требовать серверные ограничения (#197) | выкл / вкл; если вкл, сессия не стартует без impersonation или временного SA | выкл |
| Protected cluster (#417) | выкл / вкл; если вкл, повышение потолка из сессии не спрашивается: отказ с объяснением; снимается только здесь | выкл |
| Другие kind'ы (CRD) для агента (#192) | выкл / вкл; если выкл, агент читает и меняет только kind'ы из allowlist (`READABLE` / `WRITABLE`) | выкл, и в пресете «Разработка» тоже |

Значения Secrets в `get_resource`/`describe_resource`, логах и exec маскируются всегда, это не
настраивается. Значение отдаёт только инструмент раскрытия, по одному Secret и после отдельного
подтверждения пользователя (см. «Права по запросу»). Раскрытие отмечается в UI как ослабление
(`Loosened`) с предупреждением. Старые файлы настроек получают «метаданные и проверки», в том
числе бывший пресет «Разработка», остальное не меняется.

**Изменение (#9).** Доступ AI-агента теперь включён по умолчанию: строгие значения остальных
настроек (read-only, только dry-run, без exec, значения Secrets скрыты, подтверждение
контекста в окне Kubach, отказ на Protected cluster) и так ограничивают агента, а выключенный
доступ заставлял включать его вручную на каждом контексте. Включённый доступ больше не
считается ослаблением (`Loosened::McpEnabled` удалён): ни значка ⚠ в хотбаре, ни строки
«Looser than the defaults» в настройках. Выключить его можно для каждого контекста; записи в
файле настроек с явным `mcp_enabled = false` остаются выключенными, запись без этого поля
читается как включённая.

Как это сочетается с решением выше:
- Шаг 2 («временный SA») выполняется, только если временные объекты разрешены для контекста.
  Иначе после impersonation сразу идёт режим «только клиент». Значит, по умолчанию в кластере
  ничего не создаётся, и [ADR 0004](0004-local-only.md) соблюдается без оговорок; временные
  объекты — явный выбор пользователя для конкретного кластера.
- Если impersonation или временный SA настроены, но не сработали (сломанный RBAC, нет сети,
  сессия на несколько namespace), сессия не переходит в «только клиент» молча (#197): с
  «Требовать серверные ограничения» она не стартует и объясняет причину, без этой настройки
  стартует с заметным предупреждением «server-side limits are off: …» в подтверждении, в
  настройках агента и в выводе `kubach mcp`.
- Настройки ограничивают, но не расширяют: профиль сессии не может быть шире, чем разрешено
  для контекста, и не шире реальных прав пользователя (RBAC и защита от эскалации).
- Настройки привязаны к имени контекста **и** адресу API-сервера, чтобы переименование
  контекста не перенесло разрешения на другой кластер.
- Для локальных кластеров (`minikube`, `kind`, `docker-desktop`, `k3d`) UI предлагает пресет
  «Разработка», но не включает его сам.

## Права по запросу (#227)

Раньше права сессии выдавались заранее: контекст, namespace и профиль выбирались при старте.
Теперь профиль сессии — **потолок**, а права внутри него выдаются по запросу: Kubach спрашивает
пользователя в момент, когда агенту впервые понадобилось право, и запоминает ответ до конца
подключения.

```
 none ──► read(ns) ──► secret(ns, name) ──► modify(ns)
 каждая ступенька ≤ «Максимальный профиль» контекста ≤ RBAC пользователя
```

- **Подключение** — это сессия (`Session` id): сессия приложения для HTTP, жизнь процесса для
  stdio, hosted-сессия для хранилища. Разрешения и отказы хранятся в сессии и сгорают вместе с
  ней (TTL, отзыв, блокировка хранилища). Они привязаны к id сессии, а не к имени клиента:
  `client_name` агент сообщает сам, это имя только для показа. С #401 namespace при старте
  не выбирается: `read(ns)` спрашивается для любого namespace, который назвал агент (см.
  «Namespace по запросу»); отказ без вопроса — только для namespace вне закреплённых
  `kubach mcp --namespace` и сверх лимита «Число namespace в сессии».
- **Порядок проверки** не меняется: сессия жива → профиль и настройки → namespace, kind, имена
  → права. Policy остаётся чистой функцией: она получает таблицу ответов и режим сессии и
  отвечает «разрешено», «отказ» или «нужно право X» (`NeedsGrant`). Слой инструментов задаёт
  вопрос и проверяет заново. Право сверх потолка (профиль, deploy, exec, Secrets для агента;
  с #417 профиль, deploy и exec можно повысить запросом, см. ниже)
  не спрашивается — policy сразу отказывает. Отказ пользователя запоминается
  (`GrantDenied`), повторного вопроса нет. «Нет ответа» (окно закрыто, таймаут, приложение не
  запущено для stdio) отказом не считается и запомнено не будет.
- **read(ns)** покрывает чтения по профилю (логи — с debug) и метаданные и проверки Secrets,
  если контекст их разрешает. Отдельного вопроса для метаданных нет.
- **secret(ns, name)** — на каждый Secret отдельный вопрос с явным предупреждением: значение
  уйдёт в контекст модели и, как правило, провайдеру LLM, отозвать это нельзя, секрет стоит
  ротировать после работы. Ответ действует только для этого Secret в этой сессии. Доступно
  только при «Secrets для агента» = «+ раскрытие по запросу»; иначе инструмента нет в каталоге,
  policy отказывает (`RevealDisabled`), агент получает понятный отказ, а пользователь —
  уведомление в окне со ссылкой на Settings → Security этого контекста. Включить раскрытие
  можно только в настройках, не из потока вопросов.
- **modify(ns)** — один «ок» на namespace покрывает только `scale` и `rollout_restart`.
  `apply_manifest` (включая dry-run, которому на сервере нужны те же verbs), `delete_resource`
  и `exec` тоже требуют modify, но по-прежнему подтверждаются на каждый вызов, опасные поля —
  отдельно. В режиме «только клиент» modify не запоминается и не спрашивается: каждый
  мутирующий вызов подтверждается сам, как раньше.
- **Вопросы в одном окне.** Вопрос — новый вид запроса `Confirmer` (`RequestKind::Grant`), он
  идёт тем же путём, что подтверждения: в главное окно приложения, а для `kubach mcp` — через
  мост `/kubach/v1/confirm`; hosted-сессии спрашивают сразу в приложении. Одновременно
  открыт один вопрос на сессию.
- **Отзыв.** На экране сессий (Settings → AI agent) видны выданные и отклонённые права;
  выданное можно отозвать. Отзыв `read(ns)` забирает и права поверх него. Отозванное право
  считается отказом и повторно не спрашивается. Процесс `kubach mcp` узнаёт об отзыве со
  следующим heartbeat.
- **Старт сессии в UI** (с #421 — по `use_context` агента, см. ниже): профиль не выбирается (потолок — максимальный профиль контекста),
  сессия стартует без прав. С #401 — одна кнопка: контекст (по умолчанию активный в
  приложении), без namespace, без TTL (длина — настройка контекста) и без опции «сразу
  разрешить чтение». У `kubach mcp` `--profile` стал необязательным потолком, по умолчанию —
  максимум контекста.
- **`kubach mcp --grant-read`**: право read(ns) на закреплённые namespace сессии (из
  `--namespace`, а без него — namespace по умолчанию из настроек или kubeconfig, как до #401)
  считается выданным с самого старта, без вопроса в окне, поэтому чтения работают и
  без запущенного приложения, как до #227. Только read: secret и modify по-прежнему требуют
  окна. Флаг действует только в пределах настроек контекста: при выключенном «AI agent access»
  сессия не стартует, потолок профиля и «Secrets для агента» не меняются, чужой namespace не
  выдаётся. В аудите такое право записано с `decided_by: launch-args`, на экране сессий
  помечено «allowed by --grant-read» и отзывается как обычно. Для контекстов из хранилища флаг
  передаётся в `hosted/start`, и приложение применяет его по тем же правилам.

### Secrets: метаданные, проверки, раскрытие
- **Метаданные** (`list_secrets`, право read(ns)): имена, тип, ключи, размеры, возраст, какие
  поды и workload ссылаются (env, envFrom, volumes, projected, imagePullSecrets) и каких ключей
  им не хватает. Значений нет.
- **Проверки на стороне Kubach** (`check_secret`, `compare_secret_values`, право read(ns)):
  агент получает только выводы — пустое ли значение, пробелы или `\n` по краям; валидный ли
  JSON, YAML (структура), base64; URL — схема, хост и порт без userinfo, пути и query; TLS —
  сроки, CN/SAN, издатель, совпадает ли `tls.key` с `tls.crt`; `dockerconfigjson` — хосты
  registry и есть ли для них auth; совпадают ли значения двух ключей. Хэши, отпечатки и
  префиксы значений наружу не отдаются: по ним можно перебрать короткие пароли. Сравнивать
  можно только два значения из кластера, а не значение, которое прислал агент, — иначе это
  оракул для перебора.
- **Раскрытие** (`get_secret_value`: ns, name, опционально key) — по правилам secret(ns, name)
  выше; ответ ограничен 64 КиБ.
- **Аудит**: ns, name, ключи, инструмент и решение (вопросы о правах — отдельными строками
  `grant:<tool>`), **без значений**. Вывод инструментов в журнал не пишется.

### Серверная идентичность
- **Временный SA, вариант A**: Role сессии отражает ровно выданные права. Сессия стартует с
  пустой Role; каждое «ок» патчит её (read → `get/list/watch` по профилю и, если контекст
  разрешает метаданные Secrets, `get/list secrets`; secret → `get secrets` с
  `resourceNames: [<name>]`; modify → verbs профиля), отзыв убирает правила. Так API-сервер
  пропускает только то, на что пользователь согласился, даже при ошибке в Kubach. Если PATCH
  не прошёл, право не выдано, агент получает ошибку. Пользователю для этого нужен ещё `patch`
  на `roles` в namespace (проверяется SSAR при выборе режима). Какие инструменты предлагать,
  при пустой Role решает SSAR под учётными данными пользователя (потолок — его RBAC).
- **Честно о Secrets**: метаданным нужен `get`/`list` на все Secrets namespace, а API отдаёт
  их вместе со значениями. Значит, при выданном read(ns) значения проходят через Kubach, и
  граница «агент не видит значений» держится **только на Kubach**, не на API-сервере. Правило
  `resourceNames` для раскрытия на сервере ничего не добавляет к уже выданному `get secrets`;
  его смысл — Role читается как список того, на что согласился пользователь. Если это
  неприемлемо, выберите «Secrets для агента» = «нет»: тогда правил на Secrets в Role нет совсем.
- **Impersonation**: права повышаются только в пределах подготовленной администратором
  идентичности, дальше API-сервер отказывает, и агент получает его ошибку.
- **Только клиент**: без изменений, граница держится на Kubach, UI это показывает.

Запись Secrets (ввод пользователем, генерация, копирование, удаление) — см. «Запись Secrets
через пользователя» ниже (#230).

## Запись Secrets через пользователя (#230)

Агенту часто нужно создать или поменять Secret, но видеть значение ему не нужно. Поэтому
значения вводит или генерирует пользователь в окне Kubach, а агент получает только результат.

**Почему не MCP elicitation.** Там ввод идёт через клиента агента и попадает в контекст модели,
то есть к провайдеру LLM. Здесь вопрос задаёт сам Kubach в своём окне, тем же путём, что и
подтверждения: новый вид запроса `Confirmer` (`RequestKind::Secret`), для `kubach mcp` — через
мост `/kubach/v1/confirm`, hosted-сессии спрашивают сразу в приложении.

**Инструменты** (`kubach_mcp::secret_write`):

| Инструмент | Что делает | Ответ агенту |
|------------|-----------|--------------|
| `request_secret_input` (ns, name, mode `create`/`update`, тип, ключи, `removeKeys`, пояснение) | Пользователь вводит значения в форме Kubach | ключи, размеры, операция, зависимые workload |
| `copy_secret` (A → B или другое имя) | Kubach копирует данные и тип на своей стороне | ключи и размеры копии |
| `delete_secret` | Удаляет Secret после подтверждения | ключи, workload, которые на него ещё ссылаются |

- **Формы по типу.** Opaque — пары ключ–значение; `kubernetes.io/tls` — выбор файлов `.crt` и
  `.key`, Kubach проверяет, что ключ принадлежит сертификату; `kubernetes.io/dockerconfigjson` —
  registry, логин, пароль, email (`.dockerconfigjson` собирает Kubach). Создать можно только эти
  три типа; при обновлении тип берётся у существующего Secret.
- **Генератор** на каждый ключ: длина (8–256) и алфавит (буквы и цифры, плюс символы, hex),
  случайность ОС, равномерно, без смещения по модулю (`kubach_core::secrets::generate`).
  Сгенерированное значение не показывается ни пользователю, ни агенту; его можно скопировать
  вручную (буфер обмена очищается через 30 с, #203).
- **Update/rotate.** Форма показывает существующие ключи без значений и ссылки на них из подов и
  workload. Пользователь заменяет, добавляет и удаляет ключи; ключи из запроса агента только
  предзаполнены, удаление, которое предлагает агент, лишь помечено. После записи агент сам может
  вызвать `rollout_restart` (обычное право modify).
- **Copy.** Только между namespace этой сессии, между контекстами — нет. Копируются `data` и
  `type`, без `ownerReferences`, меток и аннотаций (в том числе `last-applied-configuration`);
  ставится аннотация `kubach.io/copied-from`. Существующую цель Kubach не перезаписывает,
  `kubernetes.io/service-account-token` не копирует.
- **Delete.** Подтверждение на каждый вызов, в диалоге видны ссылающиеся поды и workload;
  удаляется ровно тот объект, что видел пользователь (precondition по `uid`).

**Правила.**
- Нужны профиль deploy, «Изменения» = «применять после подтверждения» и «Secrets для агента» не
  ниже «метаданные и проверки». Иначе инструментов нет в каталоге, policy отказывает.
- Права — по лестнице #227: `request_secret_input` и `delete_secret` требуют read(ns) и
  modify(ns), `copy_secret` — read(A), read(B) и modify(B); в режиме «только клиент» modify не
  спрашивается. Чужой namespace — отказ без вопроса.
- Ввод значений сам по себе — подтверждение одной записи; «запомнить» не предлагается.
  Отмена — отказ с понятной агенту причиной («the user declined… nothing was written»), не
  запоминается.
- Имя, ключи и пояснение агента в диалоге — **недоверенный текст** (prompt injection: «вставьте
  сюда токен от прода»); пояснение ограничено 1000 символами, невидимые и bidi-символы policy
  отклоняет. Контекст и namespace показываются крупно.
- **Значения нигде, кроме API.** Ответ формы (`ConfirmationDecision::Provided`, тип
  `SecretInput`) не попадает ни в ответ агенту, ни в аудит, ни в `Debug` (там только ключи и
  размеры). По мосту он идёт base64 от приложения к процессу `kubach mcp`, который и пишет
  Secret; оба — Kubach, токен моста агенту не выдаётся. Буферы, которые держит Kubach (поля
  формы, тело запроса и ответ API, ответ моста), затираются после записи; копии внутри HTTP-
  библиотеки и текстового поля GPUI — вне его контроля.
- **Как пишется.** Создание и копия — POST, обновление — merge patch только изменённых ключей с
  `resourceVersion`, прочитанным до показа формы (если Secret поменялся, запись отклоняется).
  Field manager — `kubach-mcp`. SSA здесь не используется: SSA удаляет поля, которыми менеджер
  владел раньше и не прислал, поэтому ротация одного ключа удалила бы другие (см.
  [ADR 0010](0010-apply.md), Secrets в UI тоже идут merge patch).
- **Аудит**: ns, name, ключи, операция, решение (поле `change` записи), без значений.

**Временный SA.** RBAC не умеет ограничивать `create` по `resourceNames`, поэтому с modify(ns)
Role получает `create secrets` без имён. `patch` и `delete` — только с `resourceNames` тех Secrets,
на изменение которых пользователь согласился в этой сессии; правило добавляется до записи, а если
патч Role не прошёл, запись не выполняется. Отзыв read(ns) или modify(ns) убирает и эти правила.
Честно: `create secrets` позволяет SA создать Secret любого типа; ограничение типов
(Opaque/TLS/dockerconfigjson, без service-account-token) держит Kubach, а не API-сервер.

## Secrets через поды и allowlist kind'ов (#190, #192)

Аудит #183 нашёл два обхода, при которых Secret уходит к агенту без явного согласия.

**Secret через под (#190).** Prompt injection заставляет агента применить Job с
`envFrom: secretRef: db-creds` и `sh -c 'env | base64'`, а затем прочитать логи. RBAC сессии
(даже временный SA) это не ловит: Secret читает kubelet, а не агент. Поэтому:

- **Опасные поля.** Policy помечает в каждом документе apply (Pod, Deployment, StatefulSet,
  DaemonSet, ReplicaSet, Job, CronJob и любые другие объекты, где встретятся эти поля):
  тома `secret` и `projected.sources[].secret` («manifest reads Secret X (volume)»),
  `secretRef` (`envFrom` и Secrets других типов томов), `env[].valueFrom.secretKeyRef`
  («manifest reads key K of Secret X»), `projected.sources[].serviceAccountToken`,
  `serviceAccountName`/`serviceAccount` кроме `default` («runs as ServiceAccount Y») и
  `automountServiceAccountToken: true`. Каждая находка — отдельная строка в блоке опасных полей
  диалога («что делает — где»), и кнопка «Approve» недоступна, пока пользователь не отметит
  чекбокс (#194). Dry-run перечисляет те же строки в ответе агенту. Проверка сравнения SA с
  живым объектом (`service_account_changes`) остаётся и добавляет только то, чего policy не
  видит в манифесте.
- **`imagePullSecrets` не помечаются**: их использует kubelet для pull образа, контейнер их не
  получает, и в логах их нет. Пометка только приучила бы нажимать «да» не глядя.
- **Логи.** Варианты: (а) подтверждать логи всех подов в профиле deploy; (б) подтверждать логи
  только тех подов, которые агент сам создал или изменил в этой сессии. Выбран **(б)**. Утечка
  через логи требует, чтобы под печатал Secret; под, который агент не трогал, печатает то, что
  решил его автор, и это обычная отладка, где диалог на каждый вызов приучил бы пользователя
  подтверждать не читая (так работает (а)). А путь «применить манифест, прочитать логи» (б)
  закрывает целиком. Сессия запоминает `(namespace, kind, name)` каждого объекта, который
  `apply_manifest` применил по-настоящему (до вызова API: неудачный ответ мог всё же изменить
  объект). `get_logs` спрашивает пользователя, если в этом namespace агент что-то менял, и
  под — один из таких объектов, или его владелец (ReplicaSet → Deployment, Job → CronJob,
  StatefulSet, DaemonSet) изменён агентом, или под использует ConfigMap (`configMap`,
  `configMapRef`, `configMapKeyRef`), который агент применил: изменённый скрипт в ConfigMap
  плюс `rollout_restart` — тот же обход. Если Kubach не может прочитать под или его владельца,
  он тоже спрашивает. Без изменений в namespace лишних запросов к API нет. В диалоге — какой
  объект изменён и предупреждение, что логи несут то, что печатает манифест. Остаточный риск:
  изменение, которое не проходит через `apply_manifest` (например, данные на PVC от другого
  пода), так не отслеживается; exec подтверждается всегда и закрывает прямой путь.

**Allowlist kind'ов (#192).** Раньше `READABLE`/`WRITABLE` из `rules.rs` работали только как
Role временного SA, а клиентская политика запрещала лишь Secrets, ServiceAccount и группы
RBAC/authn/authz/certificates/admissionregistration. Агент в режиме «только клиент» мог читать
любые CRD (с кредами в spec) и применять, например, Flux `Kustomization` без
`serviceAccountName`, которую затем разворачивает контроллер с правами cluster-admin.

- Policy во **всех** режимах использует тот же allowlist: чтение — `READABLE`, изменение —
  `WRITABLE` (подресурсы вроде `deployments/scale` — только как правила Role). Денилист
  identity-объектов и Secrets действует поверх. `list_kinds` показывает только доступное.
- Остальные kind'ы — настройка контекста «Allow other kinds (CRDs)», по умолчанию выключена
  (и в пресете «Разработка»: GitOps-объект заставляет контроллер действовать со своими
  правами, это отдельный осознанный выбор). Включённая настройка отмечается как ослабление.
  Отказ агенту объясняет, где пользователь её включает. Временный SA эту настройку не
  расширяет: Role сессии строится из того же allowlist, так что API-сервер откажет в CRD; она
  действует в режимах «только клиент» и impersonation (там решает RBAC идентичности).
- **GitOps-объекты** (доступны только с этой настройкой):
  - Flux `Kustomization` (`kustomize.toolkit.fluxcd.io`) и `HelmRelease`
    (`helm.toolkit.fluxcd.io`): `spec.targetNamespace` и `spec.storageNamespace`, отличные от
    namespace сессии, — **отказ**, как у `metadata.namespace`: это то место, куда контроллер
    развернёт объекты. Не заданный `targetNamespace` — опасное поле (объекты сохраняют
    namespace из источника, которого Kubach не видит). Не заданный `serviceAccountName` —
    опасное поле: контроллер применяет со своими правами, обычно cluster-admin; заданный
    показывается как «runs as ServiceAccount». `spec.kubeConfig` — «deploys to another
    cluster». `valuesFrom` и `postBuild.substituteFrom` с `kind: Secret` — «manifest reads
    Secret X».
  - Argo CD `Application` и `ApplicationSet` (`spec.template.spec`): чужой
    `destination.namespace` — **отказ**; пустой — опасное поле. `destination.server`/`name`
    не in-cluster — «deploys to another cluster». `spec.project` всегда показывается как
    опасное поле: Argo применяет с правами своего контроллера, и границы задаёт только
    AppProject, которого Kubach не проверяет; для `default` (и без `project`) добавлено, что
    по умолчанию он разрешает всё. `AppProject` целиком — опасный объект.
  - Остальные ссылки `namespace`/`namespaces` (`sourceRef.namespace` и т. п.) по-прежнему
    разрешены, но показываются как находки.

## Namespace по запросу (#401)

Раньше сессия стартовала с namespace, выбранным в UI (или в `--namespace`), а `read(ns)`
спрашивался только для него. Пользователю приходилось заранее знать namespace и заполнять
поле, а агенту — работать в одном. Теперь:

- **Сессия стартует без namespace.** `SessionSpec.namespaces` необязателен: пусто — любой
  namespace по запросу; непусто (`kubach mcp --namespace`) — сессия закреплена за ними, как
  раньше, остальные — отказ без вопроса.
- **`list_namespaces`** — единственный инструмент, читающий что-то вне namespace: только
  имена. Список берётся учётными данными пользователя (`list namespaces`, метаданные); если
  права нет (обычно на managed-кластерах), агент получает namespace, известные Kubach:
  из kubeconfig-контекста, namespace по умолчанию из настроек и недавно открытые в Kubach
  (`state.json`), каждый с источником (`cluster`, `kubeconfig`, `kubach-settings`,
  `recently-opened`, `session`, `launch-arguments`) и состоянием (`allowed`, `refused`,
  `asked-on-first-use`, `not-in-this-session`). Это подсказки, не права.
- **Первый вызов в namespace** → policy отвечает `NeedsGrant(read(ns))`, Kubach спрашивает
  пользователя (тот же диалог, что для #227); дальше secret/modify как раньше. Имя проверяется
  как DNS-метка до вопроса: `*`, `-A`, пути, пробелы, Unicode-двойники — отказ без вопроса.
  Кластерные ресурсы и `--all-namespaces` по-прежнему запрещены. Вызов без `namespace`
  работает, когда у сессии ровно один namespace; иначе — отказ с подсказкой про
  `list_namespaces`. Для системных `kube-*` в вопросе отдельная пометка.
- **Лимит «Число namespace в сессии» = 1**: первый разрешённый namespace — единственный,
  остальные — отказ без вопроса (проверяется и в policy, и при записи права: два вопроса,
  ждавшие друг друга, не дадут двух namespace). Отказанный namespace лимит не занимает.
- **Контекст** — `--context` или контекст при старте; в UI — активный контекст приложения
  (можно выбрать другой). Потолок — максимальный профиль контекста, TTL — его длина сессии.

**Серверная граница по namespace.** Идентичность сессии больше не одна на сессию: при первом
`read(ns)` = «да» Kubach выбирает её для этого namespace по тем же правилам «Решения» и
только потом записывает право:

- impersonation — SSAR `impersonate` на идентичность, отрисованную для этого namespace
  (`{namespace}` в шаблоне);
- временный SA — SSAR на SA/Role/RoleBinding/token в этом namespace, затем свой
  `kubach-mcp-<id>` с пустой Role в этом namespace (ownerReferences на SA, как раньше; sweep
  просроченных — перед созданием). Токен и клиент у каждого namespace свои: клиент
  namespace A физически не читает namespace B (проверено на minikube тестом
  `namespaces_on_request_cluster`);
- иначе «только клиент»: namespace помечается «граница только в Kubach», и для него действуют
  правила client-only (modify не запоминается, каждое изменение подтверждается). С «Требовать
  серверные ограничения» право не выдаётся и не запоминается как отказ — агент получает
  объяснение, пользователь может починить RBAC.

Вызовы в namespace идут только клиентом его идентичности; если её нет, вызов отклоняется, а
не уходит с учётными данными пользователя. Режим в policy — по namespace (`NamespaceModes`).
`session_info`, экран сессий, `kubach mcp` в stderr и `ExternalSession` моста показывают
режим, идентичность, заметки и предупреждение по каждому namespace; аудит пишет идентичность
namespace вызова (`user` — для `list_namespaces`). Закрытие сессии удаляет SA во всех
namespace. SSAR для каталога инструментов делался под пользователем в «домашнем»
namespace (с #417 каталог по SSAR не фильтруется, см. «RBAC пользователя в момент вызова») (первый закреплённый, иначе из kubeconfig, иначе `default`): он лишь не
предлагает недоступного, границу держат policy и API-сервер.

## Открытый технический вопрос
Чтения MCP: отдельные namespace-scoped watch под идентичностью сессии (честная серверная
проверка ценой дополнительного watch) или фильтрация общего кэша (#7). Решается при реализации
#12: если для контекста работает серверная идентичность (impersonation или временный SA),
чтения идут под ней; в режиме «только клиент» достаточно фильтрации кэша.

## Подключение агента к приложению (#86)
Два транспорта, одна политика и один аудит-лог (`mcp-audit.jsonl` в каталоге настроек):

- **HTTP** в работающем приложении: `127.0.0.1:<порт>` (по умолчанию 47821, задаётся в
  Settings → AI agent), bearer-токен в файле `mcp-token` каталога настроек (права `0600`,
  на Windows — DACL только текущего пользователя), проверка `Host` и отказ запросам с
  `Origin`. Этот токен открывает только `/mcp`, мост он не открывает (#191, см. «Мост»).
  Агент работает в сессии, которую пользователь запускает в UI одной кнопкой (с #401 —
  только контекст; профиль, TTL и namespace не выбираются); без сессии инструменты отвечают
  объяснением. С #421 кнопки нет: контекст выбирает агент, пользователь соглашается в окне
  (см. «Контекст выбирает агент»).
- **stdio**: `kubach mcp [--context …] [--namespace …] [--profile …]` — тот же бинарь без окна,
  агент запускает его дочерним процессом. Контекст и профиль берутся из аргументов, иначе из
  настроек (контекст при старте) и kubeconfig; `--namespace` с #401 необязателен и
  закрепляет сессию за этими namespace, без него namespace спрашиваются по запросу; профиль по
  умолчанию read-only (с #227 — потолок, по умолчанию максимальный профиль контекста). Выключенный «AI agent access» — ошибка в stderr и выход с ненулевым
  кодом. Контексты из зашифрованного хранилища процесс сам не открывает — их сессию ведёт
  приложение (см. ниже, #121).

**Подтверждения в stdio-режиме.** У процесса `kubach mcp` нет окна, а подтверждение не может
идти через самого агента (это и есть граница доверия). Поэтому мутирующие вызовы stdio-сессии
подтверждаются в окне запущенного Kubach: процесс находит приложение по настройкам (HTTP
включён, порт) и токену моста из `mcp-bridge-token` и вызывает служебные маршруты
`/kubach/v1/*` того же HTTP-сервера (подтверждение, heartbeat сессии, завершение). Если приложение не запущено или
HTTP выключен, мутирующий вызов отклоняется с объяснением, чтения работают. С #227 первому
чтению namespace тоже нужен ответ пользователя; чтобы чтения работали без приложения, как
раньше, `kubach mcp` запускают с `--grant-read` (см. «Права по запросу»). Heartbeat (раз в
5 с) показывает stdio-сессии на экране сессий приложения; отзыв там закрывает сессию в процессе
при следующем heartbeat. Подтверждение ждёт 5 минут, затем вызов отклоняется.

## Контексты из хранилища (#121)
Импортированные контексты ([ADR 0008](0008-kubeconfig-vault.md)) доступны агенту только пока
хранилище разблокировано в приложении и только по настройкам безопасности контекста (#39).
Главное правило: **секреты хранилища никогда не попадают в процесс `kubach mcp`.**

Рассмотренные варианты для stdio:
1. *Процесс сам расшифровывает хранилище* (пароль в аргументах/stdin, Keychain). Секреты
   оказываются во втором процессе, который живёт столько, сколько хочет агент, и не знает о
   блокировке в приложении; пароль в конфиге агента хуже, чем kubeconfig рядом. Отклонён.
2. *Приложение отдаёт процессу расшифрованный kubeconfig по мосту.* Блокировка тогда держится
   на честности процесса (стереть копию по heartbeat), а между heartbeat секреты остаются в
   чужой памяти. Отклонён.
3. *Приложение ведёт сессию, процесс — только ретранслятор.* Выбран.

**Как работает.** Процесс читает только открытый заголовок `vault.kubach`
(`vault::context_names`: имена контекстов, без расшифровки, без побочных эффектов), чтобы
отличить импортированный контекст от неизвестного. Если `--context` (или контекст при старте)
есть в хранилище и нет в kubeconfig, процесс не создаёт свою сессию, а просит приложение:
`/kubach/v1/hosted/start` с аргументами командной строки. Приложение проверяет, что хранилище
разблокировано и контекст действительно импортирован, разрешает namespace/профиль/TTL по своим
настройкам (те же правила, что у stdio: «AI agent access», максимальный профиль, TTL), запускает
`Session` у себя и держит её в `HostedSessions`. Перед стартом приложение спрашивает
пользователя в окне (#191): контекст, namespace, профиль, TTL, pid процесса и имя его
процесса и родителя (кто запустил, по `ps`; pid сообщает сам процесс, это помечено в
диалоге). Отказ пользователя — ошибка для процесса, и он больше не спрашивает (нужен
перезапуск `kubach mcp`); нет ответа за 5 минут или окно закрыто — тоже ошибка, следующий
вызов агента спросит снова. Пока вопрос висит, процесс уже отвечает агенту по MCP
(инструмент-заглушка `session_info`): список инструментов сессию не стартует, её стартует
первый вызов и ждёт ответа, как ждут подтверждения. Приложение выдаёт процессу ключ сессии;
вызовы агента процесс пересылает с ним:
`hosted/tools`, `hosted/call`; раз в 5 с — `hosted/ping`, при выходе — `hosted/end`.
Подтверждения показываются сразу в окне (сессия уже в приложении), аудит пишет приложение.
На экране сессий такая сессия помечена «vault, ends when it locks»; отзыв закрывает её сразу.

- Приложение не запущено, HTTP выключен или хранилище заблокировано — процесс всё равно
  стартует: агент видит один инструмент `session_info`, который объясняет, что сделать
  (запустить Kubach, включить HTTP, разблокировать). Следующий вызов снова пробует начать
  сессию; когда получилось, процесс шлёт `notifications/tools/list_changed`. Отказ по
  настройкам (доступ выключен, профиль шире разрешённого) — ошибка в stderr и в ответе на
  каждый вызов агента; с #191 процесс при этом не выходит, потому что сессию он просит в фоне.
- **Блокировка хранилища** (вручную, по таймеру бездействия, при блокировке экрана), удаление
  записи или переименование контекста немедленно закрывают в приложении все сессии на
  контекстах, которых больше нет среди разблокированных: и hosted-сессии `kubach mcp`, и
  HTTP-сессию приложения, если она запущена на импортированном контексте (её ошибка: «vault
  was locked»). Сессия, которая стартовала в момент блокировки, проверяется ещё раз по
  завершении старта и закрывается. Процесс узнаёт об этом на следующем вызове или ping;
  после разблокировки новый вызов начинает новую сессию (заново с проверкой настроек). Отзыв
  пользователем и истёкший TTL окончательны — нужен перезапуск `kubach mcp`.
- Процесс, переставший слать ping (15 с), считается завершённым; его сессия закрывается.
- Kubeconfig-контексты приложение для `kubach mcp` не ведёт (отказ): их процесс открывает сам,
  как раньше. При совпадении имени выигрывает kubeconfig (импорт переименовывает конфликты).

## Мост: свой токен, ключ сессии, согласие пользователя (#191)
Раньше мост `/kubach/v1/*` жил под тем же `require_token`, что и `/mcp`. Токен MCP выдаётся
HTTP-агентам (команда `claude mcp add`), поэтому агент с read-only-сессией на dev мог через
`/kubach/v1/hosted/start` поднять сессию на prod-кредах из хранилища без вопроса, завершить
чужую сессию через `/ended` или `/hosted/end` и этим же снять отзыв.

Решение:
- **Свой токен моста.** Файл `mcp-bridge-token` в каталоге настроек (`0700`), сам файл `0600`
  или DACL только текущего пользователя. Приложение пишет новый токен при каждом старте
  HTTP-сервера, в UI его нет, HTTP-агентам он не выдаётся. Токен MCP открывает только `/mcp`,
  токен моста — только `/kubach/v1/*`; одинаковые токены сервер не принимает. `kubach mcp`
  перечитывает файл перед каждым запросом, поэтому переживает перезапуск приложения.
- **Ключ сессии.** Запросы о сессии несут её ключ: для stdio-сессии его выбирает процесс и
  шлёт с каждым heartbeat (приложение запоминает ключ по первому heartbeat), для hosted-сессии
  ключ выдаёт приложение в ответе `hosted/start`. Heartbeat, `/ended`, `hosted/tools|call|
  ping|end` с чужим ключом отклоняются (`403` или «неизвестная сессия»), ничего не меняя.
  Поэтому один процесс `kubach mcp` не может по id завершить, «оживить» или использовать
  чужую сессию.
- **Согласие на hosted-сессию** в окне приложения (см. выше): даже процесс с токеном моста
  не получает доступ к хранилищу без «да» пользователя.

Рассмотрен отдельный транспорт (unix socket / named pipe). Он не защищает от процессов того
же пользователя лучше, чем файл `0600` (сокет тоже доступен этому пользователю), а
кроссплатформенно требует двух реализаций (`AF_UNIX` и named pipe с DACL) и клиента без
HTTP-стека. Выигрыш — проверка pid пира (`SO_PEERCRED`/`LOCAL_PEERPID`) вместо pid со слов
процесса. Отложен: граница доверия теперь держится на отдельном токене, ключах сессий и
согласии пользователя; pid в диалоге помечен как сообщённый процессом.

**Команда для Claude Code** в настройках не содержит токена: заголовок
`Authorization: Bearer ${KUBACH_MCP_TOKEN}` (Claude Code подставляет переменные окружения в
`headers`), а переменная читается из файла `mcp-token` строкой `export … "$(cat …)"` в профиле
shell. Команда добавляет сервер с `--scope user`; рядом предупреждение не использовать
`--scope project`: `.mcp.json` коммитится в репозиторий.


## Подключение одной командой (#400)
`kubach mcp install <client>` / `uninstall <client>` и кнопки Connect / Disconnect в
Settings → AI agent прописывают в конфиг клиента сервер `kubach`: абсолютный путь к текущему
бинарю и `mcp`, stdio, **без токена** (процесс ходит в приложение через мост со своим
токеном, см. выше). Сниппеты остались свёрнутыми в «Manual setup» для прочих клиентов и HTTP.

| Клиент | Файл | Ключ | Документация |
|--------|------|------|--------------|
| Claude Code | `~/.claude.json` (scope user) | `mcpServers.kubach` (`type: stdio`, `command`, `args`) | [code.claude.com/docs/en/mcp](https://code.claude.com/docs/en/mcp) |
| Codex | `$CODEX_HOME/config.toml`, по умолчанию `~/.codex/config.toml` | `[mcp_servers.kubach]` (`command`, `args`) | [developers.openai.com/codex/mcp](https://developers.openai.com/codex/mcp) |
| OpenCode | `$XDG_CONFIG_HOME/opencode/opencode.json`, по умолчанию `~/.config/opencode/opencode.json` | `mcp.kubach` (`type: local`, `command: [...]`, `enabled`) | [opencode.ai/docs/mcp-servers](https://opencode.ai/docs/mcp-servers/), [opencode.ai/docs/config](https://opencode.ai/docs/config/) |
| Cursor | `~/.cursor/mcp.json` | `mcpServers.kubach` (`type: stdio`, `command`, `args`) | [cursor.com/docs/context/mcp](https://cursor.com/docs/context/mcp) |
| Claude Desktop | macOS `~/Library/Application Support/Claude/claude_desktop_config.json`, Windows `%APPDATA%\Claude\…`, Linux `$XDG_CONFIG_HOME/Claude/…` (официально не описан) | `mcpServers.kubach` (`command`, `args`) | [modelcontextprotocol.io/quickstart/user](https://modelcontextprotocol.io/quickstart/user) |

Файлы чужие, поэтому: изменение показывается до записи (путь и unified diff; в CLI вопрос,
`--yes` пропускает, без терминала и без `--yes` — отказ; в UI — диалог), меняется только
запись `kubach` (JSON через `serde_json` с `preserve_order` и прежним отступом, TOML через
`toml_edit` с комментариями), прежний файл сохраняется рядом как `<файл>.bak-kubach`,
повторная установка ничего не пишет, битый файл (и JSONC с комментариями у OpenCode) не
трогается и называется в ошибке, файл, изменившийся между показом и «да», не
перезаписывается, symlink остаётся symlink. Пишем файлы сами, а не через `claude mcp add` /
`codex mcp add`: так одинаковы показ, резервная копия и слияние, а тесты идут во временном
HOME. Статус клиента: подключён / не подключён / не установлен (нет его файла и папки) /
подключён к другому kubach (путь устарел, например бинарь переехал) / конфиг не читается.

## Повышение потолка по запросу (#417)

Раньше потолок (максимальный профиль, «Changes», «Commands in containers») был жёстким: агент
не видел инструментов сверх него и не мог попросить больше. Пользователь подключал агента и
просил развернуть чарт, а агент отвечал «меняющих инструментов нет» — и пользователь шёл в
настройки, не зная, что именно включить. Теперь потолок остаётся в настройках, но
повышается запросом из сессии.

```
 потолок = профиль сессии ⊔ настройки контекста ⊔ повышения в сессии
 каждое право по запросу (read/modify ns, secret) — внутри потолка ≤ RBAC пользователя
```

- **Что повышается**: три измерения `Ceiling { profile, apply, exec }` — профиль (до deploy),
  «Changes» = apply after confirmation, «Commands in containers» = confirm each. Остальные
  настройки (Secrets для агента, раскрытие, CRD, число namespace, TTL, серверные ограничения)
  запросом не меняются, только в настройках.
- **Policy** по-прежнему чистая: на вызов сверх потолка она отвечает `NeedsCeiling` и называет
  недостающее (только то, чего нет: при deploy с dry-run — только apply). Слой инструментов
  спрашивает пользователя и проверяет заново, как для `NeedsGrant`. Повышение спрашивается до
  прав namespace: потолок — общий для контекста, права — на namespace.
- **Запрос** — новый вид `RequestKind::Ceiling { raise, current, server_url }`, тем же путём, что
  подтверждения: окно приложения, для `kubach mcp` — мост `/kubach/v1/confirm`, hosted —
  сразу в приложении. Диалог: «<клиент> asks for <право> on <контекст> (namespace X)», поля
  «Asks for» и «Ceiling now», кнопки **Deny** / **Allow for this session** и галочка
  **Always allow on this cluster** (по умолчанию снята; с ней кнопка — «Allow always»).
- **Allow for this session**: повышение живёт в `Session` и сгорает с ней (TTL, отзыв, блокировка
  хранилища). Повтор того же запроса не спрашивается; отказ запоминается (`CeilingRefused`) и
  покрывает меньшие запросы; «нет ответа» не запоминается.
- **Always allow**: приложение само (не процесс `kubach mcp`) поднимает потолок контекста в
  настройках через `SecuritySettings::raise_ceiling` — только повышение, ничего не понижается
  и не трогается — и пишет след `[[security.ceiling-raise]]`: контекст, сервер, время, сессия,
  клиент и строки изменений (`max profile: read-only → deploy`, …; последние 50). След виден в
  Settings → Security контекста. Если настройки нельзя записать, ответ становится «на сессию»
  с уведомлением. Аудит MCP пишет каждое решение строкой `ceiling:<tool>` (что, контекст,
  сервер, namespace, `savedToSettings`, исход `session` / `always` / `refused` / `no-answer`).
- **Protected cluster** (новая настройка контекста, по умолчанию выкл, «строже», не входит в
  «Looser than the defaults»): запросы не показываются, policy отвечает `Protected` с
  объяснением, инструменты сверх потолка скрыты. Приложение проверяет флаг по своим настройкам
  ещё раз при получении запроса (процесс мог стартовать до включения) и отказывает без
  вопроса, показывая уведомление. Снять — только в настройках.
- **Каталог**: инструменты до deploy видны всегда (кроме protected), а сверх потолка в описании
  стоит «Requires your approval in Kubach: this needs …, beyond this session's ceiling (…)».
  `instructions` и `session_info` объясняют потолок (`ceiling.settings`, `ceiling.now`,
  `raisedForThisSession`, `savedToSettings`, `protectedCluster`).

Что не ослабляется:
- **Человек в контуре**: `apply_manifest`, `delete_resource`, `exec`, запись Secrets
  подтверждаются по одному с dry-run diff, опасные поля — отдельной галочкой; повышение не
  даёт «запомнить».
- **Права namespace** (#227, #401): повышение — не право. `read(ns)` и `modify(ns)` спрашиваются
  как раньше; при client-only `modify` не запоминается.
- **Серверная граница**: при «да» Kubach перестраивает Role временного SA каждого namespace
  сессии по новому профилю, но только из уже выданных прав (`grant_rules` с повышенным
  профилем); новые права namespace добавляются при их выдаче. Если PATCH Role не прошёл,
  потолок не повышается, Role откатывается, агент и аудит получают ошибку. Impersonation:
  идентичность отрисована при выдаче `read(ns)` и не меняется — дальше подготовленной
  администратором идентичности API-сервер не пустит, агент получит его ошибку. Client-only
  namespace остаётся помеченным, каждое изменение подтверждается.
- **Маскирование, аудит, TTL** — без изменений.

### RBAC пользователя в момент вызова (#417)
Раньше при старте сессии SSAR в «домашнем» namespace (`Capability`) прятал инструменты
(scale, delete, exec, логи, события, метрики, запись Secrets). С namespace по запросу (#401)
это неверно: в домашнем namespace прав может не быть, а в нужном — есть, и наоборот. Теперь
каталог по RBAC не фильтруется; перед действием Kubach делает SSAR под учётными данными
пользователя в namespace вызова (кэш на сессию; ошибка SSAR считается «разрешено» — границу
всё равно держит API-сервер) и при «нет» отвечает агенту «your Kubernetes account has no
right to <verb> <resource> in namespace <ns>». Это не повод спрашивать пользователя: повышение
потолка не даёт RBAC-прав. Policy и серверная граница — как были.

## Helm через агента (#418)

Агент просил «разверни Redis через Helm», а Helm-инструментов в MCP не было. Теперь они есть и
работают через тот же `helm`, что и экраны Kubach ([ADR 0006](0006-helm.md)): путь из
Settings → Tools, иначе `PATH`, иначе скачанный Kubach; без `helm` инструментов нет в каталоге.

| Инструмент | Право | Что делает |
|------------|-------|-----------|
| `helm_search_charts` | — | поиск по репозиториям, добавленным в Kubach (`repositories.yaml` и кэш индексов пользовательского helm), или версии одного `oci://` чарта |
| `helm_show_values` | — | `helm show values` чарта из добавленного репозитория или разрешённого `oci://` |
| `helm_list_releases`, `helm_release_history` | `read(ns)` | релизы namespace и ревизии релиза (хранилище релизов читается клиентом namespace) |
| `helm_install`, `helm_upgrade`, `helm_rollback`, `helm_uninstall` | потолок deploy + apply (#417), `read(ns)`, `modify(ns)` | изменение с превью и подтверждением |

Поток изменения: policy (потолок, права namespace) → источник чарта → превью → подтверждение →
выполнение → результат.
- **Источник чарта**: `repo/chart` только из репозиториев, уже добавленных в Kubach (добавляет их
  только пользователь); `oci://` — один вопрос на сессию для репозитория
  (`RequestKind::ChartSource`), отказ запоминается; пути, URL, архивы, `file://` — отказ.
- **Values** — только YAML, переданный агентом (одна mapping, до 256 КиБ), никаких путей к
  файлам; в helm идут через stdin (`--values -`). В диалоге, аудите и ответах агенту значения
  ключей с чувствительными именами (`is_sensitive_name`) заменяются на `*** (N bytes)`,
  остальное — маскированием текста. Upgrade без values сохраняет values релиза.
- **Превью**: `helm install|upgrade --dry-run=server` под идентичностью namespace; для rollback —
  манифест целевой ревизии, для uninstall — манифест текущей. Объекты проверяются: всё в
  namespace сессии (иначе отказ); кластерные (CRD, ClusterRole/Binding, webhooks, PV,
  StorageClass, Namespace, … — по discovery или списку для ещё не обслуживаемых kind'ов) и
  Role/RoleBinding чарта — `dangerous`-находки, которые пользователь отмечает отдельной
  галочкой «I understand…», иначе кнопка недоступна. `--create-namespace` — только как находка
  и не в namespace с временным SA (он там уже есть).
- **Подтверждение** (`RequestKind::Helm`): действие, релиз, чарт, версия, ревизия, под кем
  выполняется, values с маскированием, список объектов, кластерные объекты; для upgrade и
  rollback — diff манифестов, где значения Secret и чувствительных env замаскированы (те же
  правила, что для объектов агенту). «Запомнить» не предлагается.
- **Выполнение** с `--debug`: фазы helm (#382) собираются в ответ агенту и, если клиент передал
  `progressToken`, уходят MCP-уведомлениями `notifications/progress`. Ответ: статус, ревизия,
  чарт, объекты, фазы и NOTES (маскированные, до 8 КиБ).

Серверная граница:
- `--namespace` и `--kube-context` задаёт Kubach, переменные окружения пользователя, меняющие
  идентичность helm (`HELM_KUBETOKEN`, `HELM_KUBEASUSER`, `HELM_NAMESPACE`, …), сбрасываются.
- **Временный SA**: helm получает kubeconfig только с кластером (сервер, CA, TLS-имя, без
  учётных данных; файл `0600` во временном каталоге, удаляется после вызова) и короткий токен SA
  (TokenRequest, 10 мин) через `HELM_KUBETOKEN` — не в аргументах, не на диске, не агенту.
  Пока идёт превью или одобренное выполнение, Role SA расширяется «правами helm»: хранилище
  релизов (Secrets), kind'ы профиля deploy, ServiceAccounts и namespaced kind'ы превью; RBAC и
  кластерные kind'ы — никогда. После вызова Role возвращается к выданным правам. Поэтому под SA
  чарт с кластерными объектами или Role/RoleBinding отклоняется с объяснением (выключить в
  values или ставить с экрана Helm). Честно: на время вызова SA видит все Secrets namespace —
  токен есть только у процесса helm, запущенного Kubach.
- **Impersonation**: kubeconfig пользователя + `HELM_KUBEASUSER`/`HELM_KUBEASGROUPS`.
- **Только клиент**: kubeconfig пользователя, как экраны Helm; namespace помечен, каждое
  изменение подтверждается. Контекст из хранилища ([ADR 0008](0008-kubeconfig-vault.md)) не
  лежит в файле, а учётные данные на диск не пишутся — там Helm работает только под SA.
- **Аудит**: аргументы с маскированными `values`, решения о потолке, правах и источниках, код
  результата — как у остальных инструментов.

## Контекст выбирает агент (#421)

Раньше HTTP-агент работал в сессии, которую пользователь запускал в Settings → AI agent →
«Session for HTTP agents» (контекст + Start). Кнопка была согласием, но мешала: пользователь
должен был заранее знать, где агенту работать, и переключать контекст руками. Блок убран.

- **HTTP**: подключение по токену даёт обработчик без сессии с тремя инструментами —
  `session_info`, `list_contexts` (имя, API-сервер, источник `kubeconfig`/`vault`, включён ли
  доступ агента, protected, недоступен ли сейчас; без учётных данных) и `use_context`.
- **`use_context`** проверяет по настройкам приложения: контекст известен; из хранилища — только
  пока оно разблокировано; «AI agent access» включён; не Protected cluster (#417) — иначе
  понятный отказ без вопроса. Потом вопрос в окне (`RequestKind::UseContext`): «<клиент> wants
  to work in context X» [Deny] [Allow for this session]. «Да» запускает сессию как раньше
  кнопка: без namespace и прав, потолок — максимальный профиль контекста, TTL — его длина
  сессии. Отказ запоминается на 10 минут для этого контекста. Повторный `use_context` на тот
  же контекст ничего не спрашивает; на другой — спрашивает и заменяет сессию (прежняя
  закрывается, временные SA удаляются). После смены приходит `notifications/tools/list_changed`.
- **stdio**: `kubach mcp` без единого параметра (так его прописывает `kubach mcp install`)
  работает так же: `list_contexts`/`use_context`, вопрос — в окне приложения через мост; без
  запущенного приложения — отказ с подсказкой про `--context`. Контексты хранилища в этом
  режиме не выбираются (их сессию ведёт приложение, нужен `--context`). С `--context` или
  другими параметрами — как раньше.
- **«Active sessions»** показывают контекст каждой сессии, а пока HTTP-агент не выбрал
  контекст — строку «no context chosen yet».

Почему автосоздание пустой сессии не ослабляет защиту:
- пустой обработчик ничего не читает из кластера: `list_contexts` отдаёт только имена и адреса
  из kubeconfig/заголовка хранилища и флаги настроек, без учётных данных и без запросов к API;
- согласие осталось, но переехало с кнопки на запрос: без «да» в окне сессии нет, а с «да» она
  такая же пустая, как после Start — каждый namespace, раскрытие Secret, изменение и
  повышение потолка спрашиваются отдельно (#227, #401, #417);
- настройки по-прежнему ограничивают: выключенный доступ и Protected cluster отказывают без
  вопроса (приложение проверяет по своим настройкам и для запросов `kubach mcp`), заблокированное
  хранилище — отказ, блокировка закрывает сессию;
- токен HTTP открывает только `/mcp`, мост — свой токен (#191); TTL, отзыв и аудит — без
  изменений, выбор контекста виден в окне и на экране сессий.

## Минимальный доступ вместо потолка (#15)

К #417 у каждого контекста в Settings → Security было около десяти настроек агента: максимальный
профиль, изменения, exec, Secrets для агента, CRD, число namespace, TTL сессии, Protected cluster,
временные объекты и «Требовать серверные ограничения». Права и так выдавались по запросу (#227,
#401, #417), поэтому ползунки потолка мешали: пользователь не знал, что включить, а агент
упирался в потолок, которого никто не выбирал осознанно. Теперь потолка нет. У контекста есть
**минимальный доступ** — то, что агент получает без вопросов; он растёт из ответов на запросы.

```
 доступ сессии = минимальный доступ контекста ⊔ разрешённое в сессии
 ограничивает только RBAC пользователя (SSAR на каждый вызов, #417)
```

**Уровни** (по возрастанию):

| Уровень | Что входит |
|---------|-----------|
| Чтение (по умолчанию) | встроенные kind'ы (Pod, Deployment, Service, ConfigMap, Job, Ingress, events…) во **всех** namespace, без вопроса о namespace. Secrets недоступны совсем, даже метаданные |
| Отладка | плюс логи и exec |
| Изменения | плюс apply, delete, scale, rollout restart, Helm |

**Secrets** (метаданные, проверки и раскрытие значений) и **пользовательские ресурсы** (CRD —
kind'ы вне встроенного allowlist) — отдельные права: только по запросу, и тоже могут стать «по
умолчанию».

**Запрос.** Всё сверх доступа сессии агент запрашивает, Kubach спрашивает пользователя в своём
окне (вид запроса `RequestKind::Access`, путь как у #417: окно приложения, для `kubach mcp` —
мост). Кнопки **Deny** / **Allow** и галочка **«Разрешать по умолчанию»** (по умолчанию снята):
- без галочки — разрешено только в этой сессии;
- с галочкой — приложение поднимает минимальный доступ контекста в настройках (уровень
  целиком, а не право на namespace; Secret и CRD — отдельными отметками) и пишет след
  `[[security.ceiling-raise]]` (имя секции прежнее); больше об этом не спрашивают;
- отказ запоминается до конца сессии и покрывает меньшие запросы; «нет ответа» не запоминается.
Другие запущенные сессии того же контекста стартовали со старым минимумом; на такой же запрос
от них приложение отвечает без вопроса, раз настройки его уже покрывают. Понижение минимума
(«Сбросить до чтения») действует на новые сессии; запущенные сохраняют то, с чем стартовали, до
своего конца.

**Подтверждение действий остаётся** — это не запрос доступа: diff dry-run перед apply, delete и
Helm, каждая команда exec, запись Secrets. Безопасный выбор этой задачи: `scale` и
`rollout_restart` теперь тоже подтверждаются по одному (раньше одно «ок» на `modify(ns)`
избавляло от вопроса — такого «ок» больше нет). Раскрытие значений одного Secret — по-прежнему
отдельное подтверждение на каждый Secret, и только если право на Secrets выдано, а «Скрывать
значения Secret» выключено. Открытый вопрос задачи — нужно ли подтверждение при минимуме
«Изменения» — решён так: подтверждения остаются на любом уровне.

**Namespace.** Вопроса о namespace больше нет, число namespace в сессии не ограничено.
Кластерные ресурсы и вызовы по всем namespace по-прежнему запрещены; `kubach mcp --namespace`
по-прежнему закрепляет сессию за своими namespace. `read(ns)` и `modify(ns)` остались внутренним
механизмом: при первом обращении к namespace они выдаются автоматически в пределах уровня
доступа (в аудите строка `grant:<tool>` с `decided_by: access`) и запускают выбор
идентичности и Role namespace. `list_namespaces` показывает состояние `available` вместо
`asked-on-first-use`.

**Идентичность — автоматически.** При первом обращении к namespace Kubach создаёт временный
ServiceAccount (Role/RoleBinding отражают то, что сессии можно), если RBAC пользователя это
позволяет в этом namespace; иначе namespace работает под учётными данными пользователя с
ограничениями только в Kubach и пометкой «server-side limits are off: <причина>», как раньше.
Настроек «Временные объекты» и «Требовать серверные ограничения» больше нет. Честно: это меняет
умолчание [ADR 0004](0004-local-only.md) — теперь Kubach по умолчанию создаёт объекты в кластере
(SA, Role, RoleBinding сессии; удаляются при её закрытии, просроченные подчищаются sweep'ом).

**Сессия** живёт до выхода из Kubach (stdio — пока жив процесс `kubach mcp`), но не дольше 8 ч.

**`kubach mcp` (stdio)** — та же модель, минимум берётся из настроек приложения для контекста.
- `--profile read-only|debug|deploy` — теперь только ограничение этого процесса: сессия не
  получает больше этого уровня, а запросы сверх него отклоняются без вопроса. Флаг сужает и
  никогда не выдаёт.
- `--ttl` укорачивает сессию (по умолчанию и максимум — 8 ч).
- `--grant-read` оставлен для совместимости и ничего не добавляет к минимуму: чтение и так
  входит в любой минимальный доступ.
- `--namespace` закрепляет namespace, как раньше.

**Что убрано из UI и настроек:** пресеты Strict/Development и подсказка пресета для локальных
кластеров; строка «Looser than the defaults» и значок ⚠ в хотбаре — полностью, без замены
(предупреждения о доступе агента пользователю не нужны, сравнивать больше не с чем); Protected
cluster; «Максимальный профиль», «Изменения» (dry-run/apply), «Команды в контейнерах», «Secrets
для агента», «Пользовательские ресурсы», «Namespace на сессию», «Длительность сессии»,
«Временные объекты» и «Требовать серверные ограничения». `list_contexts` больше не сообщает
`protected`; `session_info` вместо `ceiling` отдаёт `access` (`minimum`, `now`,
`raisedForThisSession`, `savedToSettings`).

**Что осталось в Settings → Security контекста:**
- «Скрывать значения Secret» — настройка UI пользователя (#96), без изменений; агенту тоже не
  достаётся значение, которое скрыто от пользователя;
- «Доступ ИИ-агента» — включён по умолчанию (#9);
- «Минимальный доступ» — уровень Чтение / Отладка / Изменения, отметки «Secret» и «CRD», кнопка
  «Сбросить до чтения»;
- история поднятий (`[[security.ceiling-raise]]`).

Ключи контекста в файле настроек: `mcp_enabled`, `hide_secret_values`,
`minimum_access = "read" | "debug" | "changes"`, `minimum_secrets`, `minimum_crds`.

**Совместимость.** Старые настройки читаются без ошибок; неизвестные и прежние ключи
(`max_profile`, `deploy`, `exec`, `protected`, `agent_secrets`, `session_ttl_minutes`, …)
игнорируются и пропадают при следующем сохранении. Сохранённый потолок **не** переносится в
минимум: иначе агент молча получил бы то, о чём раньше спрашивали. Явный `mcp_enabled = false` и
`hide_secret_values` сохраняются; записи старого пресета «Разработка» без `hide_secret_values`
(до #109) по-прежнему показывают значения Secret; история поднятий остаётся.

**Аудит и каталог.** Ответ на запрос доступа пишется строкой `access:<tool>` (что, контекст,
сервер, namespace, `savedToSettings`, исход `session` / `always` / `refused` / `no-answer`) вместо
`ceiling:<tool>`. Инструменты сверх доступа видны с пометкой «Requires your approval in Kubach»;
скрыты только те, что исключает `--profile` процесса, и `get_secret_value`, пока значения Secret
скрыты.
