# 0011 — Async-рантайм и отмена задач

Статус: принято

## Контекст
`kube-rs` работает на tokio, UI — на собственном executor GPUI ([ADR 0002](0002-kube-rs.md)
оставлял границу открытой). Вся работа с кластером и внешними программами (`helm`,
`kustomize`) идёт на общем рантайме `kubach-core::runtime`, а UI ждёт результат из
`cx.spawn`. Раньше `runtime::spawn` возвращал голый `JoinHandle`: при его drop задача
продолжала работать. Закрытый экран не останавливал запрос, а Cancel в dry-run Helm не
останавливал процесс `helm` до 6-минутного таймаута — повторный клик запускал второй
параллельно (#206). Kustomize обходил это своей обёрткой `run_cancellable`.
Рантайм — два потока, и тяжёлое декодирование релизов Helm (base64 + gzip + JSON)
прямо на них тормозило watch-потоки.

## Решение
- **Модель владения.** У каждой фоновой задачи есть владелец — экран, вкладка, диалог,
  entity. `runtime::spawn` возвращает `BackgroundTask<T>`: это future (ожидание даёт
  `Result<T, JoinError>`), а его `Drop` вызывает `abort`. Владелец хранит handle — обычно
  внутри `gpui::Task`, который ждёт результат и лежит в поле entity
  (`self.preview = Some(Preview { _task, .. })`). Новый запуск заменяет поле, и старая
  задача отменяется; закрытие экрана освобождает entity, и задача отменяется вместе с ним.
- **Abort-on-drop по умолчанию.** Отмена future останавливает и то, что за ним стоит:
  закрывает HTTP-соединение или watch, а процесс, запущенный через `kubach-core::process`,
  убивается (`kill_on_drop`). Так Cancel, закрытие экрана и повторный клик dry-run Helm или
  сборки Kustomize сразу убивают процесс. Отдельные обёртки вроде `run_cancellable` не нужны.
- **`spawn_detached` — исключение с обоснованием.** Возвращает `JoinHandle`, drop которого
  лишь перестаёт ждать. Используется только там, где работа должна пережить владельца,
  и каждое место комментируется:
  - изменения, уже отправленные в кластер: `helm install/upgrade/rollback/uninstall`
    (убитый на середине `helm` оставляет релиз в `pending-*`), применение YAML (не dry-run),
    запись Secret, действие плагина, массовые действия;
  - shutdown: закрытие MCP-сессий (удаление временного ServiceAccount), остановка
    HTTP-сервера агента.
  Чтение и предпросмотр (dry-run) никогда не detached.
- **Явная остановка detached-процесса (#382).** Закрытие экрана по-прежнему не трогает
  `helm install/upgrade`, но пользователь может остановить их кнопкой Cancel в тосте
  (с подтверждением). `process::Cancel` шлёт процессу SIGTERM: Helm
  отменяет ожидание хуков и `--wait` и записывает релиз как `failed`, а не `pending-*`.
  Если процесс не вышел за `process::CANCEL_GRACE` (10 с), он убивается, и пользователь
  заранее предупреждён, что релиз может остаться `pending-*`. Rollback, uninstall и массовые
  действия Stop не получают; drain останавливается своим флагом между подами.
- **Живой вывод.** `process::run_watched` читает stdout/stderr построчно и отдаёт строки
  обработчику по мере появления. Изменения релизов Helm идут с `--debug`: по журналу
  в stderr тост показывает фазу (`Waiting for Job …`), а секции значений, хуков и
  манифеста, которые `--debug` добавляет в stdout, вырезаются (`helm::progress`).
- **Blocking-работа.** CPU-тяжёлое и блокирующее идёт на blocking-пул tokio, а не на два
  I/O-потока: декодирование релизов Helm (`helm::store`) — через `runtime::blocking`,
  проверка картинок (`images`) — через `tokio::task::spawn_blocking`. Blocking-задачу нельзя прервать: при отмене владельца она
  доделывается, но результат отбрасывается — поэтому туда кладётся только короткая работа.
- Задачи, которые и так живут, пока жив владелец (watch, стримы логов, exec,
  port-forward, опрос метрик), используют тот же `BackgroundTask` (раньше —
  `spawn_background`).

## Последствия
- Забытый handle — это отменённая задача: `#[must_use]` на `BackgroundTask` и `clippy`
  ловят `runtime::spawn(...)` без сохранения результата; fire-and-forget нужно писать
  явно через `spawn_detached`.
- `gpui::Task`, сделанный `.detach()`, держит `BackgroundTask` внутри и не даёт его
  отменить: для работы, которую надо отменять, task хранится в entity.
- Изменения в кластере не отменяются закрытием экрана, и полуприменённого состояния из-за
  закрытой вкладки не бывает; прервать install/upgrade можно только явным Cancel.
- Тесты: `runtime::tests` (drop отменяет, ожидание возвращает результат, detached
  переживает handle) и `process::tests::dropping_the_task_kills_the_process`.
