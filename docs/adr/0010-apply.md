# 0010 — Применение изменений: SSA и merge patch

Статус: принято

## Контекст
Kubach меняет объекты в кластере двумя путями: пользователь применяет YAML из редактора
(целый манифест, возможно несколько документов) и нажимает действия плагинов (scale,
restart, suspend, cordon…), которые меняют одно-два поля. Те же объекты одновременно
ведут другие участники: `kubectl`, Helm, GitOps-контроллеры, HPA. Нужно не затирать
чужие поля молча и показывать пользователю, что именно изменится.

## Решение
- **Редактор YAML — server-side apply** (`kubach-core::apply::server`). Kubach применяет
  как field manager `kubach` (`FIELD_MANAGER`), параметры — `ApplyOptions`
  (`field_manager`, `force`, `dry_run`). Перед применением всегда dry-run: сервер
  валидирует, проставляет значения по умолчанию и прогоняет admission, а редактор
  показывает diff (`kubach-app::editor::review`). Конфликт полей с другими менеджерами
  не перетирается: ошибка 409 разбирается в читаемый список полей и их владельцев,
  а пользователь может явно выбрать «Force apply» (`force: true`, забрать поля себе).
- **MCP** применяет тем же SSA, но со своим field manager `kubach-mcp`
  (`kubach_mcp::tools::FIELD_MANAGER`) и всегда без `force`: правки агента видны в
  `managedFields` отдельно от правок человека, а конфликт возвращается агенту ошибкой.
- **Действия плагинов — точечные патчи** (`kubach-core::plugin::builtin::patch` и
  аналоги в плагинах): merge patch (scale, suspend Job/CronJob, GitOps suspend/resume) или
  strategic merge patch там, где нужно слияние списков (restart, cordon). Патч содержит
  только меняемое поле и не требует полного манифеста.
- **Secrets** меняются merge patch только по изменённым ключам (`secrets::apply_patch`,
  field manager `kubach`), значения не проходят через редактор YAML. Запись Secrets агентом
  через пользователя (#230) устроена так же: создание — POST, обновление — merge patch изменённых
  ключей, field manager `kubach-mcp` ([ADR 0005](0005-mcp-permissions.md)).
  Переименование ключа Secret (#275) — тот же merge patch: старый ключ удаляется, новый
  ставится со значением из формы, поэтому переименовать можно только загруженное или
  заменённое значение.
- **ConfigMap по ключам** (#275) — второй вид того же объекта в редакторе YAML, а не отдельный
  путь: блоки ключей (`kubach-core::data_keys`) записываются в YAML-текст (меняются только
  `data` и `binaryData`), и дальше тот же dry-run, diff и SSA.

## Последствия
- Поля, которые Kubach применил через SSA, принадлежат менеджеру `kubach`; повторное
  применение манифеста без поля удаляет его, если поле больше никто не ведёт.
- Конфликт с Helm, GitOps или HPA виден до применения (dry-run) и требует явного решения;
  `force` переносит владение полем на `kubach`, и контроллер может вернуть своё значение
  при следующей синхронизации — это ответственность пользователя.
- Патчи действий плагинов не используют SSA и не заявляют владение явно: менеджер
  у них определяется сервером по умолчанию, поэтому они не конфликтуют с чужими полями,
  но и не защищены от перезаписи (например, `replicas` при работающем HPA).
- Удалённый или переименованный ключ ConfigMap, которым владеет и другой менеджер (например,
  `kubectl-create`), после SSA остаётся: ревью предупреждает «Removed but still present after
  apply».
- Агент не может перехватить чужие поля: для этого нужен человек и редактор.
