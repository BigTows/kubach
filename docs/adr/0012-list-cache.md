# 0012 — Кэш списков ресурсов на диске

Статус: принято

## Контекст
Список вида (Pods, Deployments…) появлялся только после полного list: при каждом запуске,
переключении контекста, вида или namespace — пустой экран «Loading…», на больших
кластерах — секунды. Watch при этом умирал вместе с последней подпиской, и возврат в
только что открытый namespace снова делал полный list (#300).

## Решение
- **Stale-while-revalidate.** Последний загруженный список каждого вида хранится на диске
  (`kubach-core::list_cache`) и показывается сразу, пока идёт обычный list+watch; по
  приходу полного списка он подменяется в той же таблице (выделение и прокрутка
  сохраняются). Пока обновление идёт, в статус-баре тонкий индетерминированный
  `LoadingBar` (`kubach-ui`). Без подключения или API discovery показывается
  последний список с пометкой «из кэша»; при ошибке подключения он остаётся.
- **Ключ** — контекст, `(group, kind)` и namespace (или «все namespace» для выбора всех и
  для cluster-scoped видов), как у watch. Выбор нескольких namespace собирается из записей
  по каждому; если хоть одной нет, кэш не показывается — частичный список не выдаётся за
  полный.
- **Чувствительные данные не пишутся.** Secrets не кэшируются совсем (даже с вырезанными
  значениями); у остальных объектов удаляются `managedFields` и
  `last-applied-configuration`. Кэш объектов в памяти сам их не хранит, поэтому объекты
  сериализуются как есть, без копии; объект, в котором они всё же есть, копируется без них.
- **Контексты из хранилища не кэшируются** (#178, [ADR 0008](0008-kubeconfig-vault.md)).
  Для контекста, импортированного в хранилище, на диск не пишется и с диска не читается
  ничего: ни списки, ни каталог API (`discovery::cache`). Список таких контекстов
  (`disk_cache::uncached`) приложение обновляет из открытого заголовка хранилища и из
  загруженных контекстов — он известен и при заблокированном хранилище. Проверка стоит в
  самом кэше (`ListCache::accepts`, `discovery::cache::file`), а не у вызывающих. Вид на
  таком контексте ведёт себя как вид, для которого в кэше ничего нет: «Loading…» до
  прихода списка; последний список, потерянный вместе с подключением, остаётся на экране
  из памяти.
- **Имя файла начинается с метки контекста** — `<sha256(имя контекста), 16 байт>-<хэш
  ключа>` (`disk_cache::file_name`), одинаково для списков и каталога API. По имени
  контекста его файлы находятся без чтения содержимого. `disk_cache::sweep` при старте и
  при изменении списка контекстов хранилища (импорт, переименование, удаление записи)
  удаляет в `cache/lists` и `cache/discovery` файлы таких контекстов, файлы со старыми
  именами (одна хэш-сумма без метки: по ним контекст не определить, поэтому после
  обновления кэш списков и каталогов один раз строится заново) и временные файлы
  недописанных записей старше часа. `cache/images` не трогается: там картинки по URL из
  чартов, без привязки к контексту.
- **Ограничения.** Формат с версией, gzip; запись не больше 10 000 объектов и 8 МиБ, всего
  до 200 записей и 64 МиБ, вытесняются давно не читанные. Битый файл, файл другой версии
  или другого ключа игнорируется и удаляется. Каталог — `<config dir>/cache/lists`
  (`KUBACH_CONFIG_DIR`), его чистит «Clear cache».
- **Запись в фоне.** `ListWriter` копит последний список на ключ и пишет его через
  `runtime::blocking`; чтение — на background executor GPUI. Главный поток диска не
  касается.
- **Когда пишется** (#169). Запись — это сериализация, gzip и атомарная запись всего
  списка, а читается кэш только при следующем открытии вида, поэтому свежесть в секундах
  ему не нужна:
  - первый раз — через `WRITE_DELAY` (3 с) после загрузки списка, чтобы пачка событий
    после list дала одну запись;
  - пока список меняется — не чаще раза в `WRITE_INTERVAL` (60 с) на ключ, пишется
    последний список; после долгой тишины изменение снова ждёт только `WRITE_DELAY`;
  - список, который уже записан (тот же `Arc`), повторно не пишется: вид отдаёт на запись
    все свои namespace при изменении любого из них;
  - при смене вида (другой kind, namespace, контекст), при закрытии экрана и при выходе
    из приложения ожидающие списки пишутся сразу. Выход ждёт запись столько, сколько ждёт
    GPUI; оборванная запись оставляет прежний файл (запись атомарная).
  - Список, оказавшийся больше 8 МиБ после сжатия, запоминается (число объектов и размер)
    и не сериализуется заново, пока по числу объектов он не должен уложиться в лимит
    (размер считается пропорциональным числу объектов) или пока не пройдёт 10 минут —
    объекты могли уменьшиться и при том же их числе.
  - Вытеснение (`prune`: чтение каталога и размер каждого файла) — на первой записи и
    затем раз в 8 записей; до него кэш может превышать лимиты не больше чем на 7 записей.
  - Замеры (debug-профиль, зависимости с `opt-level = 3`, macOS, Apple Silicon; 10 000
    подов по ~3 КиБ JSON, файл 1,4 МиБ): одна запись 1,75 с → 0,89 с (нет копии каждого
    объекта, сериализатор пишет в gzip через буфер); список, меняющийся каждые 150 мс,
    пишется 1 раз в минуту вместо 20.
- **Watch в памяти.** Отпущенный watch работает ещё `LINGER` (90 с, не больше 8 штук,
  вытесняется давно отпущенный) и в статус «Syncing» не входит; watch одного namespace,
  пока грузится, отдаёт объекты своего namespace из загруженного watch всех namespace.

## Последствия
- Контексты из хранилища открываются без кэша: список и каталог API каждый раз
  загружаются с сервера.
- Повторное открытие вида, кластера или namespace показывает данные мгновенно; переключение
  namespace туда-обратно не делает нового list.
- Кэшированные данные могут быть устаревшими: в строке счётчика пометка «cached N ago»,
  действия над объектами без подключения недоступны.
- Принцип «watch только у активного экрана» ослаблен на `LINGER`: несколько watch живут до
  90 с после ухода с экрана.
